OperationQueue 是不是过时了？

它确实是老概念，但没有被废弃。 NSOperationQueue 出现于 2007 年的 Mac OS X 10.5，比 GCD（2009）还早；iOS 4 起改为基于 GCD 实现。Apple 自己的框架和大量老项目仍在用它。

2021 年 Swift Concurrency 出现后，新代码里它的大部分用途都被替代了：依赖关系 → 按顺序 await；限制并发数 → TaskGroup；取消 → 结构化取消。所以现在新写的代码里确实很少用。

仍然值得用的场景：需要暂停/恢复整个队列、运行时修改最大并发数、用 KVO 观察任务状态，或者维护已有的、基于 Operation 的下载或图片处理管线。

按部署目标选择： Swift Concurrency 需要 iOS 13+；@Observable 需要 iOS 17；Mutex / Atomic 需要 iOS 18；Task.immediate 需要 iOS 26。@concurrent、nonisolated(nonsending) 是 Swift 6.2 的语言特性，取决于编译器版本和工程设置。

基础概念

概念含义
进程 / 线程线程是 CPU 调度的基本单位。iOS App 有一个主线程（UI 线程）和若干后台线程。
队列（Queue）GCD 的任务容器，FIFO。开发者面向队列而不是线程编程，由系统决定使用哪个线程。
任务（Task）Swift Concurrency 中的异步工作单元，可以挂起、恢复，可能在不同线程上恢复。
串行 vs 并发串行：同一时刻只执行一个任务。并发：可同时执行多个任务。
同步 vs 异步同步（sync）：调用方等待任务完成。异步（async）：提交后立即返回。
并发 vs 并行并发是结构（多个任务交替推进）；并行是执行（多个核心同时执行）。
阻塞 vs 挂起阻塞（block）：线程卡住什么也不做，占着线程。挂起（suspend，await）：任务让出线程，线程可以去执行其他任务。
数据竞争（Data Race）多个线程同时访问同一内存且至少一个是写，没有同步。Swift 6 在编译期消除。
竞态条件（Race Condition）结果依赖于执行时序的逻辑错误。即使没有数据竞争也可能发生（如 actor 重入）。
QoS / 优先级告诉系统任务的重要程度，影响调度与能耗。

Thread

少用Mac OS X 10.0 · 2001 / iOS 2
现状

App 代码里几乎不再手动创建 Thread：要并发用 Task，要后台队列用 GCD。只有需要“专用长期线程 + 自己的 RunLoop”时才直接用。

2.1是什么

Thread（NSThread）是对 POSIX 线程的封装，是最底层的多线程方式。

swift
let thread = Thread {
    print("在新线程中：\(Thread.current)")
}
thread.name = "com.example.worker"
thread.qualityOfService = .utility
thread.start()

Thread.isMainThread          // 当前是否主线程
Thread.sleep(forTimeInterval: 1)   // 阻塞当前线程

2.2何时使用

  • 几乎不需要在 App 代码中直接使用。
  • 极少数场景：需要一个长期存在、带自己 RunLoop 的线程（例如某些旧的网络库、需要专用线程的 C 库）。

2.3注意

  • 在 Swift Concurrency 的 async 函数中，Thread.current 已被标为不可用（Swift 6），因为任务在 await 前后可能运行在不同线程上，"当前线程"不再有意义。判断主线程隔离应使用 MainActor.assumeIsolated / MainActor.preconditionIsolated()。

2.4Thread 的闭包在哪个线程执行？

以 2.1 的代码为例，要把创建 Thread 对象和执行闭包分开看：

swift
let thread = Thread {                          // ① 创建 Thread 对象
    print("在新线程中：\(Thread.current)")      // ② 闭包：新线程的入口
}
thread.start()                                 // ③ 启动
步骤在哪个线程执行说明
① let thread = Thread { ... }当前线程（写在按钮回调 / onAppear 里就是主线程）只是在内存里创建一个 Thread 对象（“线程的描述”）。此时新线程还不存在，闭包也不会执行
② 闭包体新创建的后台线程start() 之后系统才创建一条新的 POSIX 线程，并在其上执行闭包
③ thread.start()当前线程异步：立即返回，不等闭包执行完。不调用 start()，闭包永远不会执行

所以在闭包里：

swift
Thread.isMainThread   // false
Thread.current        // <NSThread: 0x600001234567>{number = 8, name = (null)}

// 对比：在主线程打印 Thread.current
// <_NSMainThread: 0x...>{number = 1, name = main}
主线程创建 Thread 对象→start()→继续往下执行（不等待） 新线程执行闭包 print(...)→结束、线程退出
  • 闭包结束，线程就退出。想让它长期存在，需要在闭包里运行它自己的 RunLoop（即 2.2 所说的“长期存在、带自己 RunLoop 的线程”）。
  • 直接调用 thread.main() 不会开新线程：闭包会在当前线程上同步执行，和普通函数调用一样。开新线程只能用 start()。
  • 执行顺序不确定：start() 之后的主线程代码，可能比闭包里的 print 先输出。

RunLoop

底层 · 按需Mac OS X 10.0 · 2001 / iOS 2

3.1是什么

RunLoop 是线程的事件处理循环："等待事件 → 处理事件 → 休眠"。每个线程最多一个 RunLoop，只有主线程的 RunLoop 默认在运行（由 UIApplicationMain / SwiftUI App 启动）。

关键概念是 Mode（模式）：

Mode说明
.default默认模式，空闲时处于此模式
.tracking（UITrackingRunLoopMode）用户拖动/滚动 ScrollView 时切换到此模式
.common伪模式，一个"集合"，默认包含 .default 和 .tracking

一个输入源（如 Timer）只会在它被注册的模式下触发。

3.2典型场景

swift
// 1) SwiftUI 中的定时器
struct CountdownView: View {
    @State private var remaining = 60
    // in: .common —— 滚动时也继续触发（若用 .default，滚动时会暂停）
    private let timer = Timer.publish(every: 1, on: .main, in: .common).autoconnect()

    var body: some View {
        Text("\(remaining)")
            .onReceive(timer) { _ in
                if remaining > 0 { remaining -= 1 }
            }
    }
}

// 2) Combine 切换到 RunLoop.main —— 在 .default 模式执行，滚动时会被推迟
imagePublisher
    .receive(on: RunLoop.main)
    .sink { self.thumbnail = $0 }

// 3) 在指定 mode 下于下一次 RunLoop 迭代执行
RunLoop.main.perform(inModes: [.common]) { /* ... */ }

// 4) CADisplayLink（逐帧回调）
let link = CADisplayLink(target: self, selector: #selector(step))
link.add(to: .main, forMode: .common)

3.3特点

  • 最底层，没有编译期检查。
  • 与滚动强相关：注册在 .default 的任务在滚动时不执行。
  • 用于 Timer、DisplayLink、端口、perform(_:with:afterDelay:) 等依赖 RunLoop 的 API。

OperationQueue

老概念 · 少用Mac OS X 10.5 · 2007 / iOS 2
现状

老概念（2007 年），没有废弃，但新代码中很少用。大部分场景已被 TaskGroup 和结构化并发替代；需要暂停整个队列、运行时调整并发数、或维护已有 Operation 代码时仍然合适。详见文首“现状”一节。

4.1是什么

面向对象的任务队列，比 GCD 出现得早；2009 年起底层改为基于 GCD（§5）。相比 GCD 多了：依赖关系、取消、最大并发数、KVO 状态观察、暂停/恢复。

swift
let queue = OperationQueue()
queue.maxConcurrentOperationCount = 2          // 1 即串行队列
queue.qualityOfService = .utility

let download = BlockOperation { downloadFile() }
let unzip    = BlockOperation { unzipFile() }
let save     = BlockOperation { saveToDB() }

unzip.addDependency(download)                  // 依赖：download 完成后才执行 unzip
save.addDependency(unzip)

queue.addOperations([download, unzip, save], waitUntilFinished: false)

OperationQueue.main.addOperation { updateUI() } // 主队列

queue.cancelAllOperations()                    // 取消（已在运行的需自行检查 isCancelled）
queue.isSuspended = true                       // 暂停调度新的 operation

4.2何时使用

  • 有复杂依赖图、需要取消/暂停、需要限制并发数的任务（如批量下载、图片处理流水线）。
  • 新代码中，大多数场景可以用 TaskGroup + 结构化并发替代；但需要"暂停整个队列""运行时修改并发数"时，OperationQueue 仍然方便。

GCD（Grand Central Dispatch）

Mac OS X 10.6 · 2009 / iOS 4
现状

GCD 没有过时，它仍是系统的底层，Swift Concurrency 的 MainActor 也建立在主队列之上。但在新的 App 代码里，大部分 GCD 用法都有了 Swift Concurrency 的替代（见各小节标签和 §13）。仍然常用的是：DispatchQueue.main.async 与旧回调互操作、DispatchSource、concurrentPerform。

GCD 的核心思想：把任务（block）提交给队列，由系统管理线程池执行。

5.1三种队列

队列类型执行线程用途
DispatchQueue.main串行主线程UI 更新
DispatchQueue.global(qos:)并发（系统共享）线程池中的后台线程一次性的后台工作
DispatchQueue(label:)串行（默认）线程池中的后台线程保护共享状态、按顺序执行
DispatchQueue(label:, attributes: .concurrent)并发（私有）线程池中的后台线程读写锁（配合 barrier）

5.2DispatchQueue.main旧回调互操作

swift
// 旧式回调切回主线程
URLSession.shared.dataTask(with: url) { data, _, _ in
    let image = data.flatMap(UIImage.init(data:))
    DispatchQueue.main.async { self.image = image }
}.resume()

// 延迟执行
DispatchQueue.main.asyncAfter(deadline: .now() + 2) { showToast = false }

// 推迟到当前代码之后执行（例如 onAppear 后设置焦点）
.onAppear { DispatchQueue.main.async { isFocused = true } }
  • async 总是入队，等当前代码执行完之后才执行；但不保证跨过一轮 RunLoop，也不保证等到下一帧渲染之后。
  • 主队列由主 RunLoop 在 common modes 下排空，所以滚动期间也会执行。
  • 在主线程调用 DispatchQueue.main.sync → 死锁。
  • Swift 6 编译器会把传给 DispatchQueue.main.async 的闭包视为 @MainActor 隔离，可直接访问 MainActor 状态。

5.3DispatchQueue.global(qos:)→ @concurrent

系统提供的共享并发队列，按 QoS 区分：

QoS场景对应 TaskPriority
.userInteractive动画、事件处理，需立即完成— （主线程级别）
.userInitiated用户点击后等待的结果（打开文档）.userInitiated / .high

5.5并发队列 + barrier：读写锁→ actor / Mutex

final class ThreadSafeDictionary<Key: Hashable & Sendable, Value: Sendable>: @unchecked Sendable {
    private var dict: [Key: Value] = [:]
    private let queue = DispatchQueue(label: "rw", attributes: .concurrent)

    subscript(key: Key) -> Value? {

Swift Concurrency

推荐Swift 5.5 · 2021

Swift 5.5 引入、Swift 6 强制数据竞争安全的语言级并发模型。核心理念：结构化并发 + actor 隔离 + 编译期检查。

7.1async / await推荐

swift
func fetchUser(id: Int) async throws -> User {
    let (data, _) = try await URLSession.shared.data(from: url(for: id))
    return try JSONDecoder().decode(User.self, from: data)
}
  • await 是潜在挂起点：任务让出线程，等结果返回后再恢复，恢复时可能在另一个线程（但会回到正确的 actor 上）。
  • 真正挂起时任务让出线程，不阻塞；但 await 只是潜在挂起点。被调用的函数如果仍在 MainActor 上做同步计算（例如 nonsending 函数），照样会卡 UI（见 Fig. 3）。

7.2协作式线程池（Cooperative Thread Pool）

  • 非 MainActor 的任务默认跑在全局并发执行器上，底层是一个线程数受限的线程池（通常 ≈ CPU 核心数；这是观测到的实现行为，不是 API 保证）。
  • 每个线程依靠任务在 await 处主动让出来切换工作（"协作式"）。
  • 前进保证（forward progress）：任务不能无限期阻塞线程（详见下文）。因此在 async 代码中禁止：semaphore.wait()、group.wait()、Thread.sleep、长时间同步 I/O、DispatchQueue.sync 到可能等待异步任务的队列等。
  • 对比 GCD：GCD 在线程阻塞时会补充线程（可能线程爆炸）；协作池不会补充线程（阻塞会饿死）。

前进保证是什么

前进保证是 Swift Concurrency 运行时与代码之间的约定：协作线程池里的线程，永远不能停下来等待一件“还需要别的任务来完成”的事情。 任务可以在 await 处挂起、让出线程，但不能占着线程阻塞等待。

线程池之所以需要这个约定，是因为它的设计和 GCD 正好相反：

  • 线程数固定（约等于 CPU 核心数）：不超过核心数，就没有多余的线程切换开销。
  • 挂起不占线程：await 时，任务把“接下来要做的事”（续体，continuation）存进内存，线程立刻去执行别的任务；结果回来后，续体由某个空闲线程接着执行。
  • 不补线程：某个线程被阻塞时，运行时不会新开线程顶替。GCD 会补线程，代价是线程爆炸（Fig. 2 实测开到 64 个）。

所以整个设计依赖一个前提：线程只会在 await 处离开任务，不会被卡住。 一旦线程被阻塞，它就从池子里“消失”，直到阻塞解除。

违反会怎样：饿死与死锁

饿死（starvation）：被阻塞的线程不能执行任何其他任务。12 个线程都被阻塞时，所有 async 工作（其他任务、网络回调后的续体）都停住排队。Fig. 2 就是这个现象：100 个各阻塞 100ms 的任务，在 12 个线程的协作池里花了约 927ms。阻塞时间更长或没有上限时，程序看起来就像卡死了。

死锁（deadlock）：semaphore.wait() 这类操作等的是将来才会发生的事——别的任务执行完后调用 signal()。可那个任务本身也需要一个线程才能运行：

swift
func load() async -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result: Data!
    Task {
        result = await fetch()     // 这个任务需要一个空闲线程才能运行
        semaphore.signal()
    }
    semaphore.wait()               // ❌ 当前线程卡在这里，等上面的任务
    return result
}

只有一个调用时，碰巧还有空闲线程，看起来“能用”；同时有 12 个调用时，12 个线程全卡在 wait()，负责 signal() 的任务永远没有线程可用，于是永久死锁。

在 MainActor 上第一次调用就会死锁：

swift
@MainActor func onTap() {
    let semaphore = DispatchSemaphore(value: 0)
    Task {                          // 继承 MainActor → 要在主线程上执行
        await doWork()
        semaphore.signal()
    }
    semaphore.wait()                // ❌ 主线程卡住，等一个需要主线程才能运行的任务
}

Task {} 继承了 MainActor，必须等主线程空出来才能运行；主线程却卡在 wait() 等它。两边互相等待，界面同时冻结。

此外还有优先级反转：await 时运行时知道“谁在等谁”，可以提升被等待任务的优先级（§7.8）；信号量不记录将来由谁 signal()，运行时无法提升，高优先级任务可能被低优先级任务拖住。

什么样的阻塞是允许的

关键在于等的是什么：

  • ✓ 允许：等一件已经在执行、很快就会结束的事。例如 Mutex、NSLock、OSAllocatedUnfairLock 保护的短临界区——持有锁的线程已经在运行，很快就会释放；用串行队列 queue.sync { dict[key] } 快速读一个值，只要那个队列不会反过来等待 Swift 任务；很快完成的系统调用（如读一个很小的本地文件）。
  • ✕ 禁止：等一件将来才会开始、需要别的线程来执行的事（信号量、group、sync 到可能等待异步任务的队列），以及时间没有上限的等待（长时间睡眠、网络 I/O）。
  • 这也是 §10 说“持有锁时不能 await”的原因：持锁时挂起，锁可能被持有很久，其他线程只能阻塞等待。

编译器为什么不拦？怎么发现？

  • 只有少数 API 被标记为不能在 async 函数中使用（例如 Thread.current）；semaphore.wait()、group.wait() 等阻塞调用，编译器大多不会报错，只能靠约定。
  • 调试时可以把问题放大：在 Xcode 的 Scheme → Run → Arguments → Environment Variables 中设置 LIBDISPATCH_COOPERATIVE_POOL_STRICT=1（WWDC21《Swift concurrency: Behind the scenes》介绍）。它把协作池限制为单线程，任何违反前进保证的阻塞都会立即表现为卡死，在开发阶段就能暴露。

一句话总结： 协作线程池为了避免线程爆炸，把线程数固定在核心数，并约定线程只在 await 处让出。在 async 代码里阻塞线程，轻则占掉有限的线程导致饿死；如果等的是需要另一个线程才能完成的工作，就会死锁——在 MainActor 上第一次调用就会发生。等待一律用 await，阻塞只允许发生在很短、等待对象已经在运行的临界区里。

7.3Task：非结构化任务推荐

Task 是 Swift Concurrency 中最常用的入口：从同步代码（按钮回调、onAppear、委托方法）启动一段异步工作。每个 Task 有自己的优先级、TaskLocal 值和取消标志。

“非结构化”指它不是创建者的子任务：生命周期不受代码作用域约束，父任务取消也不会传播给它。需要随父任务一起结束的并行工作，应使用 async let / TaskGroup（§7.5、§7.6）。

1. 创建与获取结果

swift

    try await api.fetchItems()

4. 取消与生命周期

  • cancel() 只是设置标志，取消是协作式的：任务要自己检查 Task.isCancelled / Task.checkCancellation()，或在 Task.sleep、URLSession 等会响应取消的 API 处结束（§7.7）。
  • 闭包会强引用捕获的对象（包括 self），直到任务结束。长任务要配合取消，或用 [weak self]。
  • SwiftUI 中优先用 .task { }：视图消失时自动取消。在 onAppear 里写 Task {} 不会自动取消（演示 App 第 11 页）。

5. 常见误区

  • 以为 Task {} 会去后台：在 MainActor 上下文中 Task { heavyCPUWork() }，同步计算仍在主线程，会卡 UI（Fig. 3）。要去后台，把计算放进 @concurrent 函数，或用 Task.detached。
  • 以为丢掉句柄、或父任务取消，Task 就会停：都不会。需要取消就保存句柄，或者改用结构化并发。
  • 在循环里大量创建 Task {} 做并行：无法统一等待和取消，应使用 TaskGroup。
  • 依赖多个 Task {} 之间的执行顺序：它们是独立调度的，顺序没有保证（§12）。

    let report = await generateReport()
    await MainActor.run { self.report = report }
}
  • 不继承任何上下文，运行在全局并发执行器上。
  • 适合：确实需要与当前 actor 完全无关的后台工作。
  • 官方建议优先使用结构化并发或 nonisolated/@concurrent 函数，Task.detached 是最后手段。

7.6TaskGroup：动态数量的子任务（结构化）推荐

swift
func downloadAll(_ urls: [URL]) async throws -> [URL: Data] {
    try await withThrowingTaskGroup(of: (URL, Data).self) { group in
        for url in urls {
            group.addTask {
                let (data, _) = try await URLSession.shared.data(from: url)
                return (url, data)
            }
        }
        var result: [URL: Data] = [:]
        for try await (url, data) in group {    // 按完成顺序收集
            result[url] = data
        }
        return result
    }
}

限制并发数（替代 Semaphore）：

swift
await withTaskGroup(of: Void.self) { group in
    let maxConcurrent = 3
    var iterator = items.makeIterator()

    for _ in 0..<maxConcurrent {
        guard let item = iterator.next() else { break }
        group.addTask { await process(item) }
    }
    while await group.next() != nil {
        if let item = iterator.next() {
            group.addTask { await process(item) }
        }
    }
}
变体说明
withTaskGroup子任务不抛错
withThrowingTaskGroup子任务可抛错。子任务的错误要通过 next() / for try await 取出并从 group 闭包抛出，才会取消其余子任务，group 还要等它们实际结束才退出；若在闭包内捕获错误，其余子任务继续执行
withDiscardingTaskGroup（iOS 17+）不收集结果，子任务完成后立即释放，适合长期运行的"服务器循环"

7.10actor：保护可变状态推荐

swift
actor ImageCache {
    private var cache: [URL: UIImage] = [:]

    func image(for url: URL) -> UIImage? { cache[url] }

    func load(_ url: URL) async throws -> UIImage {
        if let cached = cache[url] { return cached }
        let (data, _) = try await URLSession.shared.data(from: url)
        let image = UIImage(data: data)!
        cache[url] = image                       // ⚠️ 见下方"重入"
        return image
    }
}

let image = try await cache.load(url)            // 外部访问必须 await
  • actor 保证同一时间只有一个任务在访问其内部状态（串行执行），从而消除数据竞争。
  • 可重入（reentrancy）：在 await 处，actor 可以去执行其他调用。所以 await 之后，之前读取的状态可能已经变化。上例中两个并发调用会重复下载同一 URL；解决方式是缓存"进行中的 Task"：
swift
actor ImageLoader {
    private var tasks: [URL: Task<UIImage, Error>] = [:]

    func load(_ url: URL) async throws -> UIImage {
        if let existing = tasks[url] { return try await existing.value }
        let task = Task { try await download(url) }
        tasks[url] = task
        return try await task.value
    }
}

7.11MainActor 与全局 actor推荐

@MainActor 是一个全局 actor，其执行器即主线程/主队列。被标注的类型、函数、属性、闭包都被隔离到主线程。

swift
@MainActor
@Observable
final class ProfileViewModel {
    var user: User?
    var isLoading = false

    func load() async {
        isLoading = true
        defer { isLoading = false }
        user = try? await api.fetchUser()   // 等待异步结果；恢复后继续在 MainActor 上执行
    }
}

注意：await 本身不决定 fetchUser() 在哪里执行，这取决于它的隔离声明。能保证的只是：load() 恢复后仍在 MainActor 上。

切换到 MainActor 的几种方式：

swift
await MainActor.run { self.title = "Done" }   // 在 MainActor 上执行一个闭包
Task { @MainActor in model.refresh() }        // 新建一个 MainActor 任务（总是入队）
MainActor.assumeIsolated { model.update() }   // 断言已在主线程（不在则崩溃），用于旧回调

SwiftUI 相关：

  • View 协议整体是 @MainActor（iOS 18 SDK 起；之前仅 body）。
  • .task {} 闭包继承 View 的隔离，即在 MainActor 上运行。

自定义全局 actor：

swift
@globalActor
actor DatabaseActor {
    static let shared = DatabaseActor()
}

@DatabaseActor
final class DatabaseStore {
    func save(_ item: Item) { ... }     // 所有成员都串行在 DatabaseActor 上
}

适合：把一组分散在多个类型中的操作统一到同一个串行隔离域。

7.12isolated 与 nonisolated：代码归属哪个 actor推荐

Swift Concurrency 中，每段代码、每个可变状态都有一个归属：属于 MainActor、属于某个 actor 实例，或者不属于任何 actor。属于某个 actor 叫 isolated（被隔离到这个 actor），不属于任何 actor 叫 nonisolated。

isolated：属于某个 actor

isolated 的代码在这个 actor 上串行执行，所以可以同步读写它的状态，不需要 await。大多数时候 isolated 是隐式的，不用写关键字：

swift
actor Bank {
    var balance = 0                  // 状态：isolated 到这个 Bank 实例

    func deposit(_ n: Int) {         // 方法：默认 isolated 到 self
        balance += n                 // 同步访问，不需要 await
    }
}

@MainActor final class ViewModel {   // 整个类 isolated 到 MainActor
    var title = ""
}

await bank.deposit(10)               // 从外部调用必须 await：跳到 Bank 上，可能要排队

isolated 也可以写成关键字，用在参数上，表示"这个函数运行在传入的 actor 上"：

swift
func withdraw(from bank: isolated Bank, amount: Int) {
    bank.balance -= amount           // 同步访问：整个函数就运行在 bank 上
}

// 继承调用方的隔离：调用方在哪个 actor 上，函数就在哪个 actor 上运行
func log(_ s: String, isolation: isolated (any Actor)? = #isolation) { ... }

#isolation 在调用处展开为调用方当前所在的 actor（不在任何 actor 上时为 nil）。通用的 async 工具函数常用它，避免每次调用都跳到别的执行器。

nonisolated：不属于任何 actor

nonisolated 的代码不能同步访问 actor 的可变状态，但调用它不需要 await：

swift
actor Bank {
    let id: String
    var balance = 0

    nonisolated var label: String {
        "Bank \(id)"                 // ✅ let 常量且是 Sendable，可以读
        // balance                   // ❌ 可变状态，nonisolated 里不能同步访问
    }
}

print(bank.label)                    // 外部同步调用，不需要 await

常见用途：

  • 实现同步协议：Hashable、CustomStringConvertible 等协议要求同步方法，actor 只能用 nonisolated 成员来实现。
  • 纯计算的工具函数：不碰任何状态，没必要绑定在某个 actor 上。
  • 退出默认的 MainActor：开启 Default Actor Isolation = MainActor 后，所有代码默认都是 @MainActor，不想属于 MainActor 的代码要显式写 nonisolated。

nonisolated 的代码在哪个线程运行？

nonisolated 只说明"不属于任何 actor"，并不等于"在后台运行"：

写法在哪里执行
nonisolated 同步函数调用方的线程：调用方在主线程，它就在主线程
nonisolated async 函数（Swift 6.2 + Approachable Concurrency）默认是 nonisolated(nonsending)，在调用方的 actor 上执行（见 §9.1）
@concurrent async 函数协作式线程池（后台）
nonisolated(unsafe) var不是执行位置，而是关闭编译器检查：线程安全由你自己保证，尽量少用

本工程中的例子

  • nonisolated struct LogEntry（Support/Console.swift）：纯数据，不属于 MainActor，任何线程都能创建。
  • Console.log 是 nonisolated func：后台线程也能直接同步调用；状态由 Mutex 保护，UI 刷新再用 Task { @MainActor in } 交回主线程。

7.13Sendable：跨隔离域传值的安全标记推荐

Sendable 表示一个值可以安全地在并发域之间传递。这里的“并发域”指同一个进程内的隔离域，和进程无关。

“并发域”是什么

Swift Concurrency 把代码划分成一个个隔离域（isolation domain），它们之间可能同时运行：

  • MainActor 是一个隔离域（主线程）。
  • 每个 actor 实例是一个独立的隔离域，比如 actor ImageCache。
  • 非隔离的并发代码（Task.detached、@concurrent 函数等）跑在后台线程池里，也是独立的。

它们都在同一个进程、同一块内存里。值会从一个域交到另一个域：调用 actor 方法时传入参数或拿到返回值、被 Task.detached 的闭包捕获、通过 AsyncStream 发送出去……之后两边可能同时拿着它。Sendable 就是一个承诺：这个值被两个域同时持有，也不会产生数据竞争。

例子一：struct 安全，传过去的是一份拷贝

swift
struct Profile: Sendable {          // 成员都是 Sendable 的 struct，会自动满足
    var name: String
    var age: Int
}

actor Store {
    func save(_ p: Profile) { /* 在 Store 上读写 p */ }
}

@MainActor func onTap(store: Store) async {
    var p = Profile(name: "Tang", age: 30)
    await store.save(p)     // ✅ 传过去的是一份拷贝
    p.age = 31              // 主线程改的是自己那份，Store 那份不受影响
}

例子二：可变 class 不安全，两边共享同一个对象

swift
final class Settings {              // 引用类型，有可变状态，不是 Sendable
    var volume = 0
}

actor Player {
    func apply(_ s: Settings) { s.volume += 1 }   // 在 Player 的线程上改
}

@MainActor func onTap(player: Player) async {
    let s = Settings()
    await player.apply(s)   // ❌ Swift 6：把非 Sendable 的 Settings 传进了另一个隔离域
    s.volume = 5            // 主线程也在改同一个对象 → 两个线程同时读写 = 数据竞争
}

class 传递的是引用，两边拿到的是同一块内存：Player 在后台线程改 volume，主线程也在改，就是 §10 演示的数据竞争（4 个线程各加 5 万次，无保护的结果只有 8 万左右）。

Swift 6 语言模式会在编译期拦下这种写法。如果编译器能证明 s 传过去之后调用方不再使用它（区域隔离，SE-0414），也会放行，因为那时其实只有一方在用它。本工程是 Swift 5 语言模式，这类问题大多只给警告或不提示。

怎样让一个类型满足 Sendable

闭包与 sending

  • @Sendable 闭包：可能在另一个隔离域里执行，所以不能捕获可变的非 Sendable 状态。Task.detached、DispatchQueue.async 的闭包都是 @Sendable。
  • sending 参数 / 返回值（Swift 6）：表示值的所有权被“转移”到另一个隔离域，转移后调用方不能再使用，从而允许传递非 Sendable 的值。

本工程中的例子

  • LogEntry：struct，成员都是 Sendable，可以在任何线程创建和传递。
  • Console：@MainActor 类，本身是 Sendable，可以被后台的 Task.detached 捕获。
  • Console.log：标了 nonisolated，把数据写进用 Mutex 保护的 LogBuffer，所以任何线程都能安全调用。

跨进程是另一回事

不同进程不共享内存，不存在“两边同时读写同一块内存”的问题。跨进程传数据需要的是序列化：把值编码成字节，再在另一边解码，用 Codable（JSON 等）、XPC、NSSecureCoding，与 Sendable 无关。Swift 中真正用于跨进程或跨网络通信的是 distributed actor，它要求参数可序列化（通常是 Codable），而不是 Sendable。

一句话总结： Sendable 回答的是“这个值在同一个进程里被两个可能同时运行的隔离域拿到，会不会数据竞争？”值类型的拷贝、不可变对象、actor、自带锁的对象都安全；共享的可变引用不安全。

在 Swift 6.2 + 默认 MainActor 隔离的工程中，推荐写法：

swift
// 默认就在 MainActor 上
final class PhotoViewModel {
    var photo: UIImage?

    func load(_ url: URL) async throws {
        let (data, _) = try await URLSession.shared.data(from: url)  // 异步 I/O：挂起，不占线程
        photo = await Self.decode(data)                               // 解码切到后台，返回后回到 MainActor
    }

    @concurrent
    nonisolated static func decode(_ data: Data) async -> UIImage? {
        // CPU 密集的解码在协作池执行，不阻塞主线程
        UIImage(data: data)?.preparingForDisplay()
    }
}

离开 MainActor 和不阻塞线程是两个不同的要求。 @concurrent 只负责把工作移出当前 actor；如果在里面做同步 I/O（如 Data(contentsOf:)），阻塞只是从主线程转移到了协作池线程。I/O 要用异步 API 等待，只把 CPU 计算交给 @concurrent。

用 Task.sleep 写周期定时器：两个常见问题

标准库没有定时器序列，常见写法是 AsyncStream + Task.sleep 循环（演示 App 第 12 页的 ticks）。它有两个特点：

1. 拖动列表不会影响它。 在 nonisolated 函数里创建的生产者 Task 跑在协作线程池上，Task.sleep 由并发运行时计时，不依赖 RunLoop 的 mode；MainActor 上的消费者通过主队列恢复，而主队列在滚动时照常排空。实测：主 RunLoop 处于 UITrackingRunLoopMode 的 1 秒内，消费者照常收到 10 个 100ms 的 tick。

真正会推迟消费者的是主线程被同步阻塞：生产者仍按时产出，AsyncStream 默认无限缓冲，主线程空出来后一次性送达。实测主线程在约 250–750ms 被阻塞时，收到时间为 [101, 202, 768, 768, 768, 768, 768, 825, …]。不想补发可以用 bufferingPolicy: .bufferingNewest(1)。

2. 实际间隔比 interval 长，而且误差会累积。 Task.sleep 只保证“至少”睡这么久，加上调度和唤醒延迟，每次都会晚一点；“每轮 yield 完再 sleep(for: interval)”会把每次的延迟累加到下一轮。

写法（20 个 tick，间隔 100ms，各测 3 次）第 20 个 tick 比理想时间晚
每轮 Task.sleep(for: interval)15.1 / 17.5 / 20.9 ms（每个约 1ms，逐渐变晚）
睡到截止时间 Task.sleep(until: next, clock:)0.8 / 1.7 / 2.3 ms（不累积，单次最多晚约 6ms）

改进写法：预先算好每个 tick 的截止时间，睡到那个时间点：

swift
let producer = Task {
    let clock = ContinuousClock()
    var next = clock.now + interval
    while true {
        do { try await Task.sleep(until: next, clock: clock) } catch { break }  // 被取消就退出
        continuation.yield(())
        next += interval
        // 落后超过一个周期（例如进程被挂起过）时跳过，不连续补发
        while next <= clock.now { next += interval }
    }
}
  • 被取消时要 break：用 try? 吞掉 Task.sleep 的取消错误，循环会继续并多发一个值（§7.7）。
  • ContinuousClock 在设备休眠期间也计时；SuspendingClock 在休眠期间暂停。按需选择。
  • Combine 的 Timer.publish 按固定时间点触发，本身没有累积误差（演示 App 第 12 页的「② 定时器」可以对比）。

常见陷阱

  1. 在 @MainActor 里用 Task {} 跑 CPU 密集型工作 → 仍在主线程，卡 UI。改用 @concurrent 函数或 Task.detached。单独写 nonisolated 不提供这个保证：nonsending 的 nonisolated async 仍在调用方 actor 上执行，同步的 nonisolated 函数也不会切换线程（见 Fig. 3）。
  2. 在 @concurrent 里做同步 I/O（如 Data(contentsOf:)）→ 主线程没卡，但协作池线程被占住，大量并发时会饿死线程池。I/O 用异步 API（URLSession.data(from:)）。
  3. 在 async 上下文中阻塞（semaphore.wait()、group.wait()、Thread.sleep、DispatchQueue.sync 等待异步结果）→ 协作池饿死/死锁。
  4. 主线程 DispatchQueue.main.sync；或对当前所在的串行队列 sync → 死锁。
  5. GCD 线程爆炸：大量阻塞任务丢进 global 队列。
  6. actor 重入：await 之后假设状态没变 → 重复下载、状态错乱。await 后重新检查状态，或缓存进行中的 Task。
  7. 忘记取消：onAppear { Task { } } 不会随视图消失而取消；用 .task {}。保存的 Task 句柄在 deinit / onDisappear 中 cancel()。
  8. 非结构化任务的 self 强引用：Task { await self.longRunning() } 会让 self 存活到任务结束。长任务需配合取消或 [weak self]。
  9. Continuation 未 resume 或 resume 两次 → 任务永远挂起 / 崩溃。
  10. 从后台线程修改 @Published 属性 → 违反 ObservableObject 的发布线程要求，出现紫色运行时警告、UI 不一致。
  11. @Observable 模型被多个线程共享修改 → 宏本身不提供隔离，也不会给出同样的警告，但会产生数据竞争。按模型声明的隔离访问它（UI 模型通常标 @MainActor）。
  12. receive(on: RunLoop.main) 导致滚动时 UI 不更新；Timer 用了 .default mode 导致滚动时停表。
  13. 依赖各种"切到主线程"方式之间的执行顺序。
  14. @unchecked Sendable 滥用：只是让编译器闭嘴，不会让代码真正线程安全。
  15. global 队列上用 barrier：无效。

以下数据于 2026-10-02 在 iPhone 17 Pro 模拟器（iOS 26.0，12 核 Mac，Debug 构建）上用临时的 Swift Testing 测试重新测量，测试串行执行、互不干扰。数字只代表这个环境，不是 API 保证。

  • nonisolated(nonsending) 与 @concurrent（10 次）：从 MainActor 调用时，前者 10/10 在主线程执行，后者 10/10 在后台线程执行。
  • 同步上下文的执行顺序（30 次）：主线程输出 30/30 都是 1 → Task.immediate → 2 → 3 → RunLoop.perform → main.async → Task {} → OperationQueue.main。Task.detached 在后台，27 次出现在 3 之后，1 次出现在 2 和 3 之间，2 次排在 main.async 之后——印证了“后台任务可能穿插在任何位置”。
  • await MainActor.run（30 次）：30/30 都是 A → Task @MainActor → B → C → D，即之前排队的 Task { @MainActor } 先于 MainActor.run 的闭包执行。结果稳定，但这仍是实现行为，不要依赖。
  • 滚动（UITrackingRunLoopMode）期间（嵌套运行主 RunLoop 0.4 秒）：DispatchQueue.main.async、Task { @MainActor }、OperationQueue.main、receive(on: DispatchQueue.main)、perform(inModes: [.common]) 都照常执行；RunLoop.main.perform（默认）、perform(inModes: [.default])、receive(on: RunLoop.main) 都推迟到回到 default mode 后才执行。.default 的 Timer 在 tracking 期间触发 0 次、回到 default 后也没有补发，.common 的 Timer 照常触发。
  • 继承：Task {} 继承 MainActor、优先级（low）和 TaskLocal；async let 继承优先级但在后台执行；Task.detached 三者都不继承（优先级为 medium）；GCD 读不到 TaskLocal。
  • 取消传播：父任务在 300ms 取消后，async let 与 TaskGroup 子任务在约 301ms 被取消；Task {} 与 Task.detached 在约 1006ms 正常完成。
  • 结构化并发耗时：顺序 await 3027ms、async let 1010ms、TaskGroup（8 个任务、限 3 个）3086ms、ThrowingTaskGroup 出错 507ms（A、B 随即被取消）。
  • 线程爆炸（100 个各阻塞 100ms 的任务，分开测各 3 次）：GCD 3 次都用了 64 个线程（约 210ms）；TaskGroup 的协作式线程池 3 次都只用了 12 个（等于核心数，约 927ms）。
  • 数据竞争（4 个线程 × 50,000 次 += 1，3 次）：无保护结果为 80,246 ~ 129,400（期望 200,000，每次都不同）；Atomic 14 ~ 16ms、Mutex 31 ~ 32ms、NSLock 36 ~ 48ms、actor 76 ~ 77ms、串行队列 sync 574 ~ 608ms。
  • actor 重入（3 次）：朴素缓存每次都下载 5 次，去重缓存每次都只下载 1 次。
