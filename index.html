OperationQueue 是不是过时了？

它确实是老概念，但没有被废弃。 NSOperationQueue 出现于 2007 年的 Mac OS X 10.5，比 GCD（2009）还早；iOS 4 起改为基于 GCD 实现。Apple 自己的框架和大量老项目仍在用它。

2021 年 Swift Concurrency 出现后，新代码里它的大部分用途都被替代了：依赖关系 → 按顺序 await；限制并发数 → TaskGroup；取消 → 结构化取消。所以现在新写的代码里确实很少用。

仍然值得用的场景：需要暂停/恢复整个队列、运行时修改最大并发数、用 KVO 观察任务状态，或者维护已有的、基于 Operation 的下载或图片处理管线。

按部署目标选择： Swift Concurrency 需要 iOS 13+；@Observable 需要 iOS 17；Mutex / Atomic 需要 iOS 18；Task.immediate 需要 iOS 26。@concurrent、nonisolated(nonsending) 是 Swift 6.2 的语言特性，取决于编译器版本和工程设置。

基础概念

概念含义
进程 / 线程线程是 CPU 调度的基本单位。iOS App 有一个主线程（UI 线程）和若干后台线程。
队列（Queue）GCD 的任务容器，FIFO。开发者面向队列而不是线程编程，由系统决定使用哪个线程。
任务（Task）Swift Concurrency 中的异步工作单元，可以挂起、恢复，可能在不同线程上恢复。
串行 vs 并发串行：同一时刻只执行一个任务。并发：可同时执行多个任务。
同步 vs 异步同步（sync）：调用方等待任务完成。异步（async）：提交后立即返回。
并发 vs 并行并发是结构（多个任务交替推进）；并行是执行（多个核心同时执行）。
阻塞 vs 挂起阻塞（block）：线程卡住什么也不做，占着线程。挂起（suspend，await）：任务让出线程，线程可以去执行其他任务。
数据竞争（Data Race）多个线程同时访问同一内存且至少一个是写，没有同步。Swift 6 在编译期消除。
竞态条件（Race Condition）结果依赖于执行时序的逻辑错误。即使没有数据竞争也可能发生（如 actor 重入）。
QoS / 优先级告诉系统任务的重要程度，影响调度与能耗。

Thread

少用Mac OS X 10.0 · 2001 / iOS 2
现状

App 代码里几乎不再手动创建 Thread：要并发用 Task，要后台队列用 GCD。只有需要“专用长期线程 + 自己的 RunLoop”时才直接用。

2.1是什么

Thread（NSThread）是对 POSIX 线程的封装，是最底层的多线程方式。

swift
let thread = Thread {
    print("在新线程中：\(Thread.current)")
}
thread.name = "com.example.worker"
thread.qualityOfService = .utility
thread.start()

Thread.isMainThread          // 当前是否主线程
Thread.sleep(forTimeInterval: 1)   // 阻塞当前线程

2.2何时使用

  • 几乎不需要在 App 代码中直接使用。
  • 极少数场景：需要一个长期存在、带自己 RunLoop 的线程（例如某些旧的网络库、需要专用线程的 C 库）。

2.3注意

  • 在 Swift Concurrency 的 async 函数中，Thread.current 已被标为不可用（Swift 6），因为任务在 await 前后可能运行在不同线程上，"当前线程"不再有意义。判断主线程隔离应使用 MainActor.assumeIsolated / MainActor.preconditionIsolated()。

2.4Thread 的闭包在哪个线程执行？

以 2.1 的代码为例，要把创建 Thread 对象和执行闭包分开看：

swift
let thread = Thread {                          // ① 创建 Thread 对象
    print("在新线程中：\(Thread.current)")      // ② 闭包：新线程的入口
}
thread.start()                                 // ③ 启动
步骤在哪个线程执行说明
① let thread = Thread { ... }当前线程（写在按钮回调 / onAppear 里就是主线程）只是在内存里创建一个 Thread 对象（“线程的描述”）。此时新线程还不存在，闭包也不会执行
② 闭包体新创建的后台线程start() 之后系统才创建一条新的 POSIX 线程，并在其上执行闭包
③ thread.start()当前线程异步：立即返回，不等闭包执行完。不调用 start()，闭包永远不会执行

所以在闭包里：

swift
Thread.isMainThread   // false
Thread.current        // <NSThread: 0x600001234567>{number = 8, name = (null)}

// 对比：在主线程打印 Thread.current
// <_NSMainThread: 0x...>{number = 1, name = main}
主线程创建 Thread 对象→start()→继续往下执行（不等待） 新线程执行闭包 print(...)→结束、线程退出
  • 闭包结束，线程就退出。想让它长期存在，需要在闭包里运行它自己的 RunLoop（即 2.2 所说的“长期存在、带自己 RunLoop 的线程”）。
  • 直接调用 thread.main() 不会开新线程：闭包会在当前线程上同步执行，和普通函数调用一样。开新线程只能用 start()。
  • 执行顺序不确定：start() 之后的主线程代码，可能比闭包里的 print 先输出。

RunLoop

底层 · 按需Mac OS X 10.0 · 2001 / iOS 2

3.1是什么

RunLoop 是线程的事件处理循环："等待事件 → 处理事件 → 休眠"。每个线程最多一个 RunLoop，只有主线程的 RunLoop 默认在运行（由 UIApplicationMain / SwiftUI App 启动）。

关键概念是 Mode（模式）：

Mode说明
.default默认模式，空闲时处于此模式
.tracking（UITrackingRunLoopMode）用户拖动/滚动 ScrollView 时切换到此模式
.common伪模式，一个"集合"，默认包含 .default 和 .tracking

一个输入源（如 Timer）只会在它被注册的模式下触发。

3.2典型场景

swift
// 1) SwiftUI 中的定时器
struct CountdownView: View {
    @State private var remaining = 60
    // in: .common —— 滚动时也继续触发（若用 .default，滚动时会暂停）
    private let timer = Timer.publish(every: 1, on: .main, in: .common).autoconnect()

    var body: some View {
        Text("\(remaining)")
            .onReceive(timer) { _ in
                if remaining > 0 { remaining -= 1 }
            }
    }
}

// 2) Combine 切换到 RunLoop.main —— 在 .default 模式执行，滚动时会被推迟
imagePublisher
    .receive(on: RunLoop.main)
    .sink { self.thumbnail = $0 }

// 3) 在指定 mode 下于下一次 RunLoop 迭代执行
RunLoop.main.perform(inModes: [.common]) { /* ... */ }

// 4) CADisplayLink（逐帧回调）
let link = CADisplayLink(target: self, selector: #selector(step))
link.add(to: .main, forMode: .common)

3.3特点

  • 最底层，没有编译期检查。
  • 与滚动强相关：注册在 .default 的任务在滚动时不执行。
  • 用于 Timer、DisplayLink、端口、perform(_:with:afterDelay:) 等依赖 RunLoop 的 API。

OperationQueue

老概念 · 少用Mac OS X 10.5 · 2007 / iOS 2
现状

老概念（2007 年），没有废弃，但新代码中很少用。大部分场景已被 TaskGroup 和结构化并发替代；需要暂停整个队列、运行时调整并发数、或维护已有 Operation 代码时仍然合适。详见文首“现状”一节。

4.1是什么

面向对象的任务队列，比 GCD 出现得早；2009 年起底层改为基于 GCD（§5）。相比 GCD 多了：依赖关系、取消、最大并发数、KVO 状态观察、暂停/恢复。

swift
let queue = OperationQueue()
queue.maxConcurrentOperationCount = 2          // 1 即串行队列
queue.qualityOfService = .utility

let download = BlockOperation { downloadFile() }
let unzip    = BlockOperation { unzipFile() }
let save     = BlockOperation { saveToDB() }

unzip.addDependency(download)                  // 依赖：download 完成后才执行 unzip
save.addDependency(unzip)

queue.addOperations([download, unzip, save], waitUntilFinished: false)

OperationQueue.main.addOperation { updateUI() } // 主队列

queue.cancelAllOperations()                    // 取消（已在运行的需自行检查 isCancelled）
queue.isSuspended = true                       // 暂停调度新的 operation

4.2何时使用

  • 有复杂依赖图、需要取消/暂停、需要限制并发数的任务（如批量下载、图片处理流水线）。
  • 新代码中，大多数场景可以用 TaskGroup + 结构化并发替代；但需要"暂停整个队列""运行时修改并发数"时，OperationQueue 仍然方便。

GCD（Grand Central Dispatch）

Mac OS X 10.6 · 2009 / iOS 4
现状

GCD 没有过时，它仍是系统的底层，Swift Concurrency 的 MainActor 也建立在主队列之上。但在新的 App 代码里，大部分 GCD 用法都有了 Swift Concurrency 的替代（见各小节标签和 §13）。仍然常用的是：DispatchQueue.main.async 与旧回调互操作、DispatchSource、concurrentPerform。

5.5并发队列 + barrier：读写锁→ actor / Mutex

swift
final class ThreadSafeDictionary<Key: Hashable & Sendable, Value: Sendable>: @unchecked Sendable {
    private var dict: [Key: Value] = [:]
    private let queue = DispatchQueue(label: "rw", attributes: .concurrent)

    subscript(key: Key) -> Value? {
        get { queue.sync { dict[key] } }                       // 多个读可并发
        set { queue.async(flags: .barrier) { self.dict[key] = newValue } }  // 写独占
    }
}

Swift Concurrency

推荐Swift 5.5 · 2021

Swift 5.5 引入、Swift 6 强制数据竞争安全的语言级并发模型。核心理念：结构化并发 + actor 隔离 + 编译期检查。

7.1async / await推荐

swift
func fetchUser(id: Int) async throws -> User {
    let (data, _) = try await URLSession.shared.data(from: url(for: id))
    return try JSONDecoder().decode(User.self, from: data)
}
  • await 是潜在挂起点：任务让出线程，等结果返回后再恢复，恢复时可能在另一个线程（但会回到正确的 actor 上）。
  • 真正挂起时任务让出线程，不阻塞；但 await 只是潜在挂起点。被调用的函数如果仍在 MainActor 上做同步计算（例如 nonsending 函数），照样会卡 UI（见 Fig. 3）。

7.2协作式线程池（Cooperative Thread Pool）

  • 非 MainActor 的任务默认跑在全局并发执行器上，底层是一个线程数受限的线程池（通常 ≈ CPU 核心数；这是观测到的实现行为，不是 API 保证）。
  • 每个线程依靠任务在 await 处主动让出来切换工作（"协作式"）。
  • 前进保证（forward progress）：任务不能无限期阻塞线程（详见下文）。因此在 async 代码中禁止：semaphore.wait()、group.wait()、Thread.sleep、长时间同步 I/O、DispatchQueue.sync 到可能等待异步任务的队列等。
  • 对比 GCD：GCD 在线程阻塞时会补充线程（可能线程爆炸）；协作池不会补充线程（阻塞会饿死）。

前进保证是什么

前进保证是 Swift Concurrency 运行时与代码之间的约定：协作线程池里的线程，永远不能停下来等待一件“还需要别的任务来完成”的事情。 任务可以在 await 处挂起、让出线程，但不能占着线程阻塞等待。

线程池之所以需要这个约定，是因为它的设计和 GCD 正好相反：

  • 线程数固定（约等于 CPU 核心数）：不超过核心数，就没有多余的线程切换开销。
  • 挂起不占线程：await 时，任务把“接下来要做的事”（续体，continuation）存进内存，线程立刻去执行别的任务；结果回来后，续体由某个空闲线程接着执行。
  • 不补线程：某个线程被阻塞时，运行时不会新开线程顶替。GCD 会补线程，代价是线程爆炸（Fig. 2 实测开到 64 个）。

所以整个设计依赖一个前提：线程只会在 await 处离开任务，不会被卡住。 一旦线程被阻塞，它就从池子里“消失”，直到阻塞解除。

违反会怎样：饿死与死锁

饿死（starvation）：被阻塞的线程不能执行任何其他任务。12 个线程都被阻塞时，所有 async 工作（其他任务、网络回调后的续体）都停住排队。Fig. 2 就是这个现象：100 个各阻塞 100ms 的任务，在 12 个线程的协作池里花了约 927ms。阻塞时间更长或没有上限时，程序看起来就像卡死了。

死锁（deadlock）：semaphore.wait() 这类操作等的是将来才会发生的事——别的任务执行完后调用 signal()。可那个任务本身也需要一个线程才能运行：

swift
func load() async -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result: Data!
    Task {
        result = await fetch()     // 这个任务需要一个空闲线程才能运行
        semaphore.signal()
    }
    semaphore.wait()               // ❌ 当前线程卡在这里，等上面的任务
    return result
}

只有一个调用时，碰巧还有空闲线程，看起来“能用”；同时有 12 个调用时，12 个线程全卡在 wait()，负责 signal() 的任务永远没有线程可用，于是永久死锁。

在 MainActor 上第一次调用就会死锁：

swift
@MainActor func onTap() {
    let semaphore = DispatchSemaphore(value: 0)
    Task {                          // 继承 MainActor → 要在主线程上执行
        await doWork()
        semaphore.signal()
    }
    semaphore.wait()                // ❌ 主线程卡住，等一个需要主线程才能运行的任务
}

Task {} 继承了 MainActor，必须等主线程空出来才能运行；主线程却卡在 wait() 等它。两边互相等待，界面同时冻结。

此外还有优先级反转：await 时运行时知道“谁在等谁”，可以提升被等待任务的优先级（§7.8）；信号量不记录将来由谁 signal()，运行时无法提升，高优先级任务可能被低优先级任务拖住。

逐条说明为什么禁止

操作问题后果
semaphore.wait()等待将来某个任务的 signal()，而那个任务需要线程才能运行死锁、饿死、优先级反转
group.wait()同上：等 group 里的任务完成，那些任务也需要线程死锁、饿死
Thread.sleep / usleep不依赖别人，不会死锁；但线程什么也不做却被占着饿死、吞吐下降。应改用 Task.sleep：挂起，不占线程
长时间同步 I/O（Data(contentsOf:) 读网络 URL、同步网络请求、慢速文件读取）线程卡在系统调用里，等待时间没有上限饿死
DispatchQueue.sync 到可能等待异步任务的队列sync 要等那个队列执行到这个 block；如果那个队列正在等某个 Swift 任务，而那个任务又需要当前线程形成等待环 → 死锁

什么样的阻塞是允许的

关键在于等的是什么：

  • ✓ 允许：等一件已经在执行、很快就会结束的事。例如 Mutex、NSLock、OSAllocatedUnfairLock 保护的短临界区——持有锁的线程已经在运行，很快就会释放；用串行队列 queue.sync { dict[key] } 快速读一个值，只要那个队列不会反过来等待 Swift 任务；很快完成的系统调用（如读一个很小的本地文件）。
  • ✕ 禁止：等一件将来才会开始、需要别的线程来执行的事（信号量、group、sync 到可能等待异步任务的队列），以及时间没有上限的等待（长时间睡眠、网络 I/O）。
  • 这也是 §10 说“持有锁时不能 await”的原因：持锁时挂起，锁可能被持有很久，其他线程只能阻塞等待。

    await withCheckedContinuation { continuation in
        ioQueue.async {                         // 阻塞发生在 GCD 线程上，不占协作池

编译器为什么不拦？怎么发现？

  • 只有少数 API 被标记为不能在 async 函数中使用（例如 Thread.current）；semaphore.wait()、group.wait() 等阻塞调用，编译器大多不会报错，只能靠约定。
  • 调试时可以把问题放大：在 Xcode 的 Scheme → Run → Arguments → Environment Variables 中设置 LIBDISPATCH_COOPERATIVE_POOL_STRICT=1（WWDC21《Swift concurrency: Behind the scenes》介绍）。它把协作池限制为单线程，任何违反前进保证的阻塞都会立即表现为卡死，在开发阶段就能暴露。

一句话总结： 协作线程池为了避免线程爆炸，把线程数固定在核心数，并约定线程只在 await 处让出。在 async 代码里阻塞线程，轻则占掉有限的线程导致饿死；如果等的是需要另一个线程才能完成的工作，就会死锁——在 MainActor 上第一次调用就会发生。等待一律用 await，阻塞只允许发生在很短、等待对象已经在运行的临界区里。

7.3Task：非结构化任务推荐

Task 是 Swift Concurrency 中最常用的入口：从同步代码（按钮回调、onAppear、委托方法）启动一段异步工作。每个 Task 有自己的优先级、TaskLocal 值和取消标志。

“非结构化”指它不是创建者的子任务：生命周期不受代码作用域约束，父任务取消也不会传播给它。需要随父任务一起结束的并行工作，应使用 async let / TaskGroup（§7.5、§7.6）。

1. 创建与获取结果

swift
// 从同步上下文进入异步世界
Button("刷新") {
    Task { await viewModel.refresh() }
}

// 保存句柄：获取结果、取消
let task = Task(priority: .userInitiated) { () -> [Item] in
    try await api.fetchItems()
}
let items = try await task.value      // 等待结果；Task<[Item], Error>
let result = await task.result        // 或拿到 Result，不抛错
task.cancel()
  • 创建后立即被调度，不需要像 Thread 那样调用 start()。
  • 丢掉 Task 句柄不会取消它（与 Combine 的 AnyCancellable 不同）：不保存返回值，任务照样运行到结束。
  • Task.detached 是“不继承任何上下文”的版本，见 §7.4。

2. 在主线程还是后台线程运行？

看 Task { } 写在什么上下文里，而不是运行时调用它的线程。它继承所在位置的 actor 隔离，这由编译器静态决定。

在哪里写 Task { … }闭包的隔离执行线程

显式标注，如 Task { @MainActor in … }以标注为准由标注决定
swift
struct ContentView: View {              // View 是 @MainActor
    func tap() {
        Task { heavyWork() }            // 主线程 —— 会卡 UI
    }
}

    func refresh() {
        Task { self.reload() }          // 在 Cache 这个 actor 上（后台线程）
    }
}

    Task { heavyWork() }                // 无隔离 → 后台线程池
    Task { @MainActor in update() }     // 显式指定 → 主线程
}

继承的是隔离，不是线程：nonisolated 函数即使碰巧在主线程上被调用，里面的 Task {} 也在后台运行；@MainActor 方法即使是从后台 await 进来的，里面的 Task {} 也一定在主线程。

线程是逐段决定的：闭包里的同步代码跑在闭包自己的隔离上；await 调用别的函数时，被调用者按它自己的隔离执行（@MainActor → 主线程；@concurrent → 后台；nonisolated(nonsending) → 留在当前 actor；其他 actor 的方法 → 那个 actor）；await 返回后再回到闭包的隔离。

swift
enum Decoder {
    @concurrent                          // 关键：声明为 @concurrent
    static func decode(_ raw: Data) async -> Item { ... }
}

Task {                                   // 在 MainActor 上创建 → 主线程

                                         // 这期间 Task 挂起，主线程空闲
    label = data.title                   // decode 返回后，回到 MainActor（主线程）
}

4. 取消与生命周期

  • cancel() 只是设置标志，取消是协作式的：任务要自己检查 Task.isCancelled / Task.checkCancellation()，或在 Task.sleep、URLSession 等会响应取消的 API 处结束（§7.7）。
  • 闭包会强引用捕获的对象（包括 self），直到任务结束。长任务要配合取消，或用 [weak self]。
  • SwiftUI 中优先用 .task { }：视图消失时自动取消。在 onAppear 里写 Task {} 不会自动取消（演示 App 第 11 页）。

5. 常见误区

  • 以为 Task {} 会去后台：在 MainActor 上下文中 Task { heavyCPUWork() }，同步计算仍在主线程，会卡 UI（Fig. 3）。要去后台，把计算放进 @concurrent 函数，或用 Task.detached。
  • 以为丢掉句柄、或父任务取消，Task 就会停：都不会。需要取消就保存句柄，或者改用结构化并发。
  • 在循环里大量创建 Task {} 做并行：无法统一等待和取消，应使用 TaskGroup。
  • 依赖多个 Task {} 之间的执行顺序：它们是独立调度的，顺序没有保证（§12）。

实验：Task 闭包本体 vs 闭包里调用的 nonisolated async 函数

“Task 会不会继承调用者的隔离”和“async 函数会不会继承调用者的隔离”是两个问题，经常被混为一谈。下面的程序把两者放在一起，用 Swift 6.4 工具链、Swift 6 语言模式分别在两种设置下编译运行：

swift
import Foundation

// Thread.isMainThread 在 async 上下文中不可用，用同步的 nonisolated 属性包一层
extension Thread { nonisolated static var isMain: Bool { Thread.isMainThread } }

nonisolated func plainAsync() async {
    print("nonisolated async func -> isMain:", Thread.isMain)
}

@MainActor
func caller() async {
    Task {
        // 闭包本体：不捕获 self，也不调用任何 MainActor API
        print("Task body -> isMain:", Thread.isMain)
        MainActor.assertIsolated()   // 如果没有继承 MainActor，这里会崩溃
        await plainAsync()
    }
    try? await Task.sleep(for: .milliseconds(200))
}

@main struct App {
    static func main() async { await caller() }
}
编译设置Task 闭包本体闭包里 await 的 nonisolated async 函数
swiftc -swift-version 6主线程后台线程
+ -enable-upcoming-feature NonisolatedNonsendingByDefault主线程主线程

结论：

  • Task 闭包本体继承创建处的全局 actor 隔离：两种设置下都在主线程上，MainActor.assertIsolated() 也没有崩溃。闭包不需要捕获 self。
  • 变化的只是被调用的 nonisolated async 函数：旧语义下它会切到全局并发执行器；开启 SE-0461（NonisolatedNonsendingByDefault，包含在 Xcode 26 的 Approachable Concurrency 里）后，它留在调用者的 actor 上。
  • 网上常见的“async task 不继承调用者隔离”的说法（例如 SwiftLee 的 Swift 6.2 concurrency changes），指的是第二列的 nonisolated async 函数，不是 Task { } 闭包。文中的 func performAsync() async 虽然没写 nonisolated，但它没有任何隔离标注，所在模块也没开默认 MainActor 隔离，所以隐式就是 nonisolated，和这里显式写 nonisolated 的 plainAsync() 等价。反过来，如果模块的 Default Actor Isolation 设为 MainActor，同样一行声明会被推断成 @MainActor，无论哪种设置都在主线程上运行。
“总会继承”的三个限定

1. 继承依据的是创建 Task 的那个上下文，不是所在的类型：在 @MainActor 类型的 nonisolated 方法里创建的 Task {} 不会继承。

2. 闭包本体被隔离，不代表它里面 await 的函数也在同一处运行：被调用函数看它自己的声明（上表第二列）。

3. 闭包显式标注了别的隔离（如 Task { @concurrent in … }）时，以显式标注为准。普通 actor 实例则要求闭包用到 self 才会隔离到该 actor。

7.6TaskGroup：动态数量的子任务（结构化）推荐

swift
func downloadAll(_ urls: [URL]) async throws -> [URL: Data] {
    try await withThrowingTaskGroup(of: (URL, Data).self) { group in
        for url in urls {
            group.addTask {
                let (data, _) = try await URLSession.shared.data(from: url)
                return (url, data)
            }
        }
        var result: [URL: Data] = [:]
        for try await (url, data) in group {    // 按完成顺序收集
            result[url] = data
        }
        return result
    }
}

限制并发数（替代 Semaphore）：

await withTaskGroup(of: Void.self) { group in
    let maxConcurrent = 3
    var iterator = items.makeIterator()

    for _ in 0..<maxConcurrent {
        guard let item = iterator.next() else { break }
        group.addTask { await process(item) }
    }
    while await group.next() != nil {
        if let item = iterator.next() {
            group.addTask { await process(item) }
        }

withThrowingTaskGroup子任务可抛错。子任务的错误要通过 next() / for try await 取出并从 group 闭包抛出，才会取消其余子任务，group 还要等它们实际结束才退出；若在闭包内捕获错误，其余子任务继续执行
withDiscardingTaskGroup（iOS 17+）不收集结果，子任务完成后立即释放，适合长期运行的"服务器循环"

7.10actor：保护可变状态推荐

swift
actor ImageCache {
    private var cache: [URL: UIImage] = [:]

    func image(for url: URL) -> UIImage? { cache[url] }

    func load(_ url: URL) async throws -> UIImage {
        if let cached = cache[url] { return cached }
        let (data, _) = try await URLSession.shared.data(from: url)
        let image = UIImage(data: data)!
        cache[url] = image                       // ⚠️ 见下方"重入"
        return image
    }
}

let image = try await cache.load(url)            // 外部访问必须 await
  • actor 保证同一时间只有一个任务在访问其内部状态（串行执行），从而消除数据竞争。
  • 可重入（reentrancy）：在 await 处，actor 可以去执行其他调用。所以 await 之后，之前读取的状态可能已经变化。上例中两个并发调用会重复下载同一 URL；解决方式是缓存"进行中的 Task"：
swift
actor ImageLoader {
    private var tasks: [URL: Task<UIImage, Error>] = [:]

    func load(_ url: URL) async throws -> UIImage {
        if let existing = tasks[url] { return try await existing.value }
        let task = Task { try await download(url) }
        tasks[url] = task
        return try await task.value
    }
}

7.11MainActor 与全局 actor推荐

@MainActor 是一个全局 actor，其执行器即主线程/主队列。被标注的类型、函数、属性、闭包都被隔离到主线程。

swift
@MainActor
@Observable
final class ProfileViewModel {
    var user: User?
    var isLoading = false

    func load() async {
        isLoading = true
        defer { isLoading = false }
        user = try? await api.fetchUser()   // 等待异步结果；恢复后继续在 MainActor 上执行
    }
}

注意：await 本身不决定 fetchUser() 在哪里执行，这取决于它的隔离声明。能保证的只是：load() 恢复后仍在 MainActor 上。

切换到 MainActor 的几种方式：

swift
await MainActor.run { self.title = "Done" }   // 在 MainActor 上执行一个闭包
Task { @MainActor in model.refresh() }        // 新建一个 MainActor 任务（总是入队）
MainActor.assumeIsolated { model.update() }   // 断言已在主线程（不在则崩溃），用于旧回调

SwiftUI 相关：

  • View 协议整体是 @MainActor（iOS 18 SDK 起；之前仅 body）。
  • .task {} 闭包继承 View 的隔离，即在 MainActor 上运行。

自定义全局 actor：

swift

    static let shared = DatabaseActor()
}

适合：把一组分散在多个类型中的操作统一到同一个串行隔离域。

7.12isolated 与 nonisolated：代码归属哪个 actor推荐

Swift Concurrency 中，每段代码、每个可变状态都有一个归属：属于 MainActor、属于某个 actor 实例，或者不属于任何 actor。属于某个 actor 叫 isolated（被隔离到这个 actor），不属于任何 actor 叫 nonisolated。

isolated：属于某个 actor

isolated 的代码在这个 actor 上串行执行，所以可以同步读写它的状态，不需要 await。大多数时候 isolated 是隐式的，不用写关键字：

swift
actor Bank {
    var balance = 0                  // 状态：isolated 到这个 Bank 实例

    func deposit(_ n: Int) {         // 方法：默认 isolated 到 self
        balance += n                 // 同步访问，不需要 await
    }
}

@MainActor final class ViewModel {   // 整个类 isolated 到 MainActor
    var title = ""
}

await bank.deposit(10)               // 从外部调用必须 await：跳到 Bank 上，可能要排队

isolated 也可以写成关键字，用在参数上，表示"这个函数运行在传入的 actor 上"：

swift
func withdraw(from bank: isolated Bank, amount: Int) {
    bank.balance -= amount           // 同步访问：整个函数就运行在 bank 上
}

// 继承调用方的隔离：调用方在哪个 actor 上，函数就在哪个 actor 上运行
func log(_ s: String, isolation: isolated (any Actor)? = #isolation) { ... }

#isolation 在调用处展开为调用方当前所在的 actor（不在任何 actor 上时为 nil）。通用的 async 工具函数常用它，避免每次调用都跳到别的执行器。

nonisolated：不属于任何 actor

nonisolated 的代码不能同步访问 actor 的可变状态，但调用它不需要 await：

swift
actor Bank {
    let id: String
    var balance = 0

    nonisolated var label: String {
        "Bank \(id)"                 // ✅ let 常量且是 Sendable，可以读
        // balance                   // ❌ 可变状态，nonisolated 里不能同步访问
    }
}

print(bank.label)                    // 外部同步调用，不需要 await

常见用途：

  • 实现同步协议：Hashable、CustomStringConvertible 等协议要求同步方法，actor 只能用 nonisolated 成员来实现。
  • 纯计算的工具函数：不碰任何状态，没必要绑定在某个 actor 上。
  • 退出默认的 MainActor：开启 Default Actor Isolation = MainActor 后，所有代码默认都是 @MainActor，不想属于 MainActor 的代码要显式写 nonisolated。

nonisolated 的代码在哪个线程运行？

nonisolated 只说明"不属于任何 actor"，并不等于"在后台运行"：

写法在哪里执行
nonisolated 同步函数调用方的线程：调用方在主线程，它就在主线程
nonisolated async 函数（Swift 6.2 + Approachable Concurrency）默认是 nonisolated(nonsending)，在调用方的 actor 上执行（见 §9.1）
@concurrent async 函数协作式线程池（后台）
nonisolated(unsafe) var不是执行位置，而是关闭编译器检查：线程安全由你自己保证，尽量少用

7.13Sendable：跨隔离域传值的安全标记推荐

Sendable 表示一个值可以安全地在并发域之间传递。这里的“并发域”指同一个进程内的隔离域，和进程无关。

“并发域”是什么

Swift Concurrency 把代码划分成一个个隔离域（isolation domain），它们之间可能同时运行：

  • MainActor 是一个隔离域（主线程）。
  • 每个 actor 实例是一个独立的隔离域，比如 actor ImageCache。
  • 非隔离的并发代码（Task.detached、@concurrent 函数等）跑在后台线程池里，也是独立的。

它们都在同一个进程、同一块内存里。值会从一个域交到另一个域：调用 actor 方法时传入参数或拿到返回值、被 Task.detached 的闭包捕获、通过 AsyncStream 发送出去……之后两边可能同时拿着它。Sendable 就是一个承诺：这个值被两个域同时持有，也不会产生数据竞争。

例子一：struct 安全，传过去的是一份拷贝

swift
struct Profile: Sendable {          // 成员都是 Sendable 的 struct，会自动满足
    var name: String
    var age: Int
}

actor Store {
    func save(_ p: Profile) { /* 在 Store 上读写 p */ }
}

@MainActor func onTap(store: Store) async {
    var p = Profile(name: "Tang", age: 30)
    await store.save(p)     // ✅ 传过去的是一份拷贝
    p.age = 31              // 主线程改的是自己那份，Store 那份不受影响
}

例子二：可变 class 不安全，两边共享同一个对象

swift
final class Settings {              // 引用类型，有可变状态，不是 Sendable
    var volume = 0
}

actor Player {
    func apply(_ s: Settings) { s.volume += 1 }   // 在 Player 的线程上改
}

@MainActor func onTap(player: Player) async {
    let s = Settings()
    await player.apply(s)   // ❌ Swift 6：把非 Sendable 的 Settings 传进了另一个隔离域
    s.volume = 5            // 主线程也在改同一个对象 → 两个线程同时读写 = 数据竞争
}

class 传递的是引用，两边拿到的是同一块内存：Player 在后台线程改 volume，主线程也在改，就是 §10 演示的数据竞争（4 个线程各加 5 万次，无保护的结果只有 8 万左右）。

Swift 6 语言模式会在编译期拦下这种写法。如果编译器能证明 s 传过去之后调用方不再使用它（区域隔离，SE-0414），也会放行，因为那时其实只有一方在用它。本工程是 Swift 5 语言模式，这类问题大多只给警告或不提示。

闭包与 sending

  • @Sendable 闭包：可能在另一个隔离域里执行，所以不能捕获可变的非 Sendable 状态。Task.detached、DispatchQueue.async 的闭包都是 @Sendable。
  • sending 参数 / 返回值（Swift 6）：表示值的所有权被“转移”到另一个隔离域，转移后调用方不能再使用，从而允许传递非 Sendable 的值。

本工程中的例子

  • LogEntry：struct，成员都是 Sendable，可以在任何线程创建和传递。
  • Console：@MainActor 类，本身是 Sendable，可以被后台的 Task.detached 捕获。
  • Console.log：标了 nonisolated，把数据写进用 Mutex 保护的 LogBuffer，所以任何线程都能安全调用。

跨进程是另一回事

不同进程不共享内存，不存在“两边同时读写同一块内存”的问题。跨进程传数据需要的是序列化：把值编码成字节，再在另一边解码，用 Codable（JSON 等）、XPC、NSSecureCoding，与 Sendable 无关。Swift 中真正用于跨进程或跨网络通信的是 distributed actor，它要求参数可序列化（通常是 Codable），而不是 Sendable。

一句话总结： Sendable 回答的是“这个值在同一个进程里被两个可能同时运行的隔离域拿到，会不会数据竞争？”值类型的拷贝、不可变对象、actor、自带锁的对象都安全；共享的可变引用不安全。

            case .failure(let error):    continuation.resume(throwing: error)
            }
        }
    }
}

用 Task.sleep 写周期定时器：两个常见问题

标准库没有定时器序列，常见写法是 AsyncStream + Task.sleep 循环（演示 App 第 12 页的 ticks）。它有两个特点：

1. 拖动列表不会影响它。 在 nonisolated 函数里创建的生产者 Task 跑在协作线程池上，Task.sleep 由并发运行时计时，不依赖 RunLoop 的 mode；MainActor 上的消费者通过主队列恢复，而主队列在滚动时照常排空。实测：主 RunLoop 处于 UITrackingRunLoopMode 的 1 秒内，消费者照常收到 10 个 100ms 的 tick。

真正会推迟消费者的是主线程被同步阻塞：生产者仍按时产出，AsyncStream 默认无限缓冲，主线程空出来后一次性送达。实测主线程在约 250–750ms 被阻塞时，收到时间为 [101, 202, 768, 768, 768, 768, 768, 825, …]。不想补发可以用 bufferingPolicy: .bufferingNewest(1)。

2. 实际间隔比 interval 长，而且误差会累积。 Task.sleep 只保证“至少”睡这么久，加上调度和唤醒延迟，每次都会晚一点；“每轮 yield 完再 sleep(for: interval)”会把每次的延迟累加到下一轮。

写法（20 个 tick，间隔 100ms，各测 3 次）第 20 个 tick 比理想时间晚
每轮 Task.sleep(for: interval)15.1 / 17.5 / 20.9 ms（每个约 1ms，逐渐变晚）
睡到截止时间 Task.sleep(until: next, clock:)0.8 / 1.7 / 2.3 ms（不累积，单次最多晚约 6ms）

改进写法：预先算好每个 tick 的截止时间，睡到那个时间点：

swift
let producer = Task {
    let clock = ContinuousClock()
    var next = clock.now + interval
    while true {
        do { try await Task.sleep(until: next, clock: clock) } catch { break }  // 被取消就退出
        continuation.yield(())
        next += interval
        // 落后超过一个周期（例如进程被挂起过）时跳过，不连续补发
        while next <= clock.now { next += interval }
    }
}
  • 被取消时要 break：用 try? 吞掉 Task.sleep 的取消错误，循环会继续并多发一个值（§7.7）。
  • ContinuousClock 在设备休眠期间也计时；SuspendingClock 在休眠期间暂停。按需选择。
  • Combine 的 Timer.publish 按固定时间点触发，本身没有累积误差（演示 App 第 12 页的「② 定时器」可以对比）。

执行时机与滚动行为

12.1主线程上的三层：RunLoop.main、DispatchQueue.main、MainActor

主线程上不只有这三种调度方式，但所有方式最终都落在同一条线程、同一个 RunLoop 上。这三者不是并列的三个调度器，而是上下叠在一起的三层：

  • RunLoop.main：主线程上一直在转的循环，是最底层。
  • DispatchQueue.main：这个循环每一圈都会处理的一个任务队列。
  • MainActor：一条规则——"这段代码只能在主线程运行"。编译器检查这条规则；需要切换到主线程时，运行时把任务放进 DispatchQueue.main。

一个比喻

主线程是唯一的一名店员：

  • RunLoop.main 是他的工作循环：看有没有顾客（触摸事件）、看闹钟（Timer）、看收件筐，做完就打个盹，有事再被叫醒。
  • DispatchQueue.main 是柜台上的一个收件筐：谁都可以往里放活儿，他每转一圈就把筐里的活儿依次做掉。
  • MainActor 是工牌上的规定："这些活只能由这名店员做"，由编译器检查。如果你本来就是这名店员，就直接做，不用放进筐里；如果你是别人（后台线程），这份活就会被放进收件筐。

主线程每一圈在做什么（简化）

主线程（只有一条）
└─ RunLoop.main：一直在转的循环，每一圈大致做这些事：
   ① 处理触摸、手势等事件
   ② 触发到期的 Timer / CADisplayLink（受 Mode 影响）
   ③ 执行 RunLoop.main.perform { } 的 block（受 Mode 影响）
   ④ 执行 DispatchQueue.main 里排队的任务（滚动时也照常执行）
        ├─ DispatchQueue.main.async { } 的 block
        ├─ OperationQueue.main 的 operation
        └─ MainActor 的任务：Task { @MainActor in }、await 之后回到主线程继续执行
   ⑤ 休眠前，Core Animation 提交本圈的 UI 修改
   ⑥ 没事就休眠，等下一个事件来唤醒

真实的处理顺序比这复杂，这里只是示意。重点是：①–⑥ 都在同一条主线程上，一次只能做一件事。

三者的区别

RunLoop.mainDispatchQueue.mainMainActor
是什么主线程的事件循环GCD 的主串行队列绑定主线程的全局 actor（隔离规则）
层次最底层由 RunLoop 每圈执行需要切换时，把任务放进主队列
检查时机运行时运行时编译期 + 运行时

区别一：MainActor 是编译期的规则，另外两个只是运行时调度。用 DispatchQueue.main 时，切没切回主线程靠你自己记得；用 MainActor 时，由编译器保证。

swift
@MainActor final class ViewModel { var title = "" }

func background(vm: ViewModel) {
    vm.title = "x"                         // ❌ 编译错误：不在 MainActor 上
}

DispatchQueue.global().async {
    DispatchQueue.main.async { label.text = "x" }   // 编译器不管你有没有切回主线程
}

区别二：已经在主线程时，MainActor 不排队。MainActor 首先是"代码属于谁"的规则，只有在需要切换线程时才发生调度。

swift
@MainActor func update() { ... }

// 当前已在 MainActor 上
update()                                   // 直接执行，就是一次普通的函数调用
DispatchQueue.main.async { update() }      // 排进主队列，这一段代码执行完后才轮到
Task { @MainActor in update() }            // 同样是新建一个任务排队

区别三：滚动时的表现不同（RunLoop Mode）。手指拖动列表时，主 RunLoop 切到 UITrackingRunLoopMode：RunLoop.main.perform { }、默认模式下的 Timer、receive(on: RunLoop.main) 都会暂停，松手后才执行；主队列在所有 common 模式下都会被处理，所以 DispatchQueue.main 和 MainActor 的任务滚动时照常执行（实测见 §12.3、演示 App 第 3 页）。

区别四：MainActor 和 DispatchQueue.main 共用同一个主队列。Task { @MainActor in } 和 DispatchQueue.main.async { } 进的是同一个队列，await MainActor.run { } 也不会插到已排队的任务前面。实测中它们按入队顺序执行，但这是实现细节，不是 API 保证，不要依赖（见 §12.2）。

主线程上的其他调度方式

它们都建立在上面两层之上（各自是否延后、滚动时是否执行，见 §11.3 的对照表）：

怎么选

  1. 新代码：给 UI 相关的类型和函数标 @MainActor。开启默认 MainActor 隔离的工程里，这已经是默认行为。
  2. 旧回调要回到主线程：用 Task { @MainActor in }；确定回调本来就在主线程上时，用 MainActor.assumeIsolated。
  3. 只在跟 GCD 代码打交道时：用 DispatchQueue.main.async。
  4. 需要和滚动、帧同步的定时（Timer、CADisplayLink）：才用 RunLoop.main，并注意 Mode（.common）。

常见陷阱

  1. 在 @MainActor 里用 Task {} 跑 CPU 密集型工作 → 仍在主线程，卡 UI。改用 @concurrent 函数或 Task.detached。单独写 nonisolated 不提供这个保证：nonsending 的 nonisolated async 仍在调用方 actor 上执行，同步的 nonisolated 函数也不会切换线程（见 Fig. 3）。
  2. 在 @concurrent 里做同步 I/O（如 Data(contentsOf:)）→ 主线程没卡，但协作池线程被占住，大量并发时会饿死线程池。I/O 用异步 API（URLSession.data(from:)）。
  3. 在 async 上下文中阻塞（semaphore.wait()、group.wait()、Thread.sleep、DispatchQueue.sync 等待异步结果）→ 协作池饿死/死锁。
  4. 主线程 DispatchQueue.main.sync；或对当前所在的串行队列 sync → 死锁。
  5. GCD 线程爆炸：大量阻塞任务丢进 global 队列。
  6. actor 重入：await 之后假设状态没变 → 重复下载、状态错乱。await 后重新检查状态，或缓存进行中的 Task。
  7. 忘记取消：onAppear { Task { } } 不会随视图消失而取消；用 .task {}。保存的 Task 句柄在 deinit / onDisappear 中 cancel()。
  8. 非结构化任务的 self 强引用：Task { await self.longRunning() } 会让 self 存活到任务结束。长任务需配合取消或 [weak self]。
  9. Continuation 未 resume 或 resume 两次 → 任务永远挂起 / 崩溃。
  10. 从后台线程修改 @Published 属性 → 违反 ObservableObject 的发布线程要求，出现紫色运行时警告、UI 不一致。
  11. @Observable 模型被多个线程共享修改 → 宏本身不提供隔离，也不会给出同样的警告，但会产生数据竞争。按模型声明的隔离访问它（UI 模型通常标 @MainActor）。
  12. receive(on: RunLoop.main) 导致滚动时 UI 不更新；Timer 用了 .default mode 导致滚动时停表。
  13. 依赖各种"切到主线程"方式之间的执行顺序。
  14. @unchecked Sendable 滥用：只是让编译器闭嘴，不会让代码真正线程安全。
  15. global 队列上用 barrier：无效。

一页速览

视频开头就给了一个容易被忽略的前提：很多 App 只需要少量并发，有些根本不需要。并发代码比单线程代码复杂，所以应该在真正遇到性能问题时才引入。大型 App 最后可能长成“主线程 + 后台任务 + 若干 actor”的结构，但没有人从那里起步，也不是每个 App 都要走到那一步。

起点

所有代码默认跑在主线程上。新建的 Xcode 26 App 项目已默认开启“main actor 隔离”模式。

异步 ≠ 并发

把函数改成 async、调用 await，就能在等待时让出主线程。自己的代码仍是单线程的，后台工作由 URLSession 这类库替你完成。

先测再搬

UI 卡顿时先用 Instruments 找原因；能不靠并发提速就先提速，实在不行才用 @concurrent 把工作移到后台。

编译器把关

值在 actor 与任务之间传递时，编译器做 Sendable 检查，在编译期指出数据竞争，而不是等到运行时崩溃。

actor 是最后一步

只有当主线程上的数据多到引发争用时，才把某个非 UI 子系统（比如网络管理）拆成自己的 actor。

两个构建设置

所有项目开启 Approachable Concurrency；以 UI 为主的模块（例如 App 主模块）把默认 actor 隔离设为 MainActor。

01

从单线程开始

程序启动时，代码在主线程上运行；只要你不明确引入并发，新增的代码也一直留在主线程上。单线程代码同一时间只做一件事，最容易写也最容易维护。主线程同时负责接收 UI 事件并刷新 UI，所以如果 App 没有大量计算，把所有东西都放在主线程上完全没问题。

1.1main actor：主线程及其数据

在 Swift 并发模型里，主线程和它的所有数据由 main actor 代表。main actor 上没有并发，因为能运行它的只有一条主线程。用 @MainActor 标注的代码或数据，Swift 保证只在主线程上运行、只从主线程访问，这叫作代码被隔离（isolated）到 main actor。

1.2默认 main actor 隔离

开启这个模式后，相当于编译器替你在模块里的每个声明上都写了 @MainActor。这样你可以从任何地方随意访问静态变量这类共享状态，在真正引入并发之前不用操心并发访问。这个模式由构建设置控制，Xcode 26 新建的 App 项目默认开启，主要用于 App 主模块和以 UI 交互为主的模块。视频后面的所有示例都假设它已开启。

    }
}

整个函数一口气在主线程上跑完，没有任何并发。只要每一步都够快，这就是最好的写法。

02

异步任务：隐藏延迟

本地文件换成网络地址后，就得用 URLSession 下载。如果在主线程上同步等待下载，UI 会一直冻结到数据返回。保持 App 响应的原则是：不要让主线程长时间被占住。等待数据这类高延迟操作，正是异步任务的用武之地。

swift
func fetchAndDisplayImage(url: URL) async throws {
    let (data, _) = try await URLSession.shared.data(from: url)  // ← 可能挂起
    let image = decodeImage(data)
    view.displayImage(image)
}

2.1await：把函数切成两段

await 标出函数可能挂起的位置：函数在当前线程上停下，等它在等的事件发生后再继续执行。可以把函数想成被切成两段，一段运行到开始下载为止，另一段在下载完成后运行。两段之间，主线程可以去做别的事，UI 因此保持响应。

值得注意的是，到这一步我们自己的代码仍然没有引入并发。URLSession 这类库会在内部把工作放到后台，我们只是采用了 async/await。

2.2Task：端到端完成一个操作

async 函数运行在任务（task）中。任务独立于其他代码执行，应当为一个具体操作从头到尾创建，常见的做法是响应某个事件，比如按钮点击。

swift
Button("加载") {
    Task {   // 继承 main actor：除了下载，其余步骤都在主线程上
        try await model.fetchAndDisplayImage(url: url)
    }
}

2.3交错执行（interleaving）

App 里可以同时有很多异步任务。比如再加一个“抓取新闻 → 显示 → 等待刷新”的任务。下载在后台进行，但两个任务的其余步骤都在主线程上，一次只能跑一个。任务彼此独立，于是轮流使用主线程：哪个任务的下一段先准备好，主线程就先跑哪个。单条线程在多个任务之间切换，就叫交错执行。它让线程不必空等某一个操作，从而更充分地利用系统资源。

异步、单线程，对很多 App 来说已经足够。
03

引入并发：@concurrent

现在下载已在后台，但解码还在主线程上。图片很大时，解码可能导致 UI 卡顿。视频给出的判断顺序是：

  1. App 不够流畅，说明主线程上的工作太多。用 Instruments 找出时间花在哪里。
  2. 如果能不靠并发让它变快，先这么做。
  3. 实在快不了，再引入并发：让一部分代码在后台线程上与主线程并行运行，同时也能用上更多 CPU 核心。

3.1给函数加 @concurrent

在默认 main actor 模式下，fetchAndDisplayImage 和 decodeImage 都隔离在 main actor 上。给 decodeImage 加上 @concurrent，就是告诉 Swift：这个函数在后台运行。

函数挪了位置，它能访问的状态也随之改变。decodeImage 原本会查一个存放在 main actor 上的缓存字典，这只在主线程上安全，于是编译器直接指出了这处对 main actor 数据的访问。这正是安全引入并发所需要的信息。

3.4写库的人：优先 nonisolated

如果解码是一个供许多客户端使用的库 API，@concurrent 未必是好选择。解码耗时取决于数据量，小数据在主线程上解码完全可以。对库来说，最好提供 nonisolated API，让调用方决定要不要卸载到后台。nonisolated 代码在哪儿调用就在哪儿运行，非常灵活，是通用库的好默认值。

swift
// 库：不替调用方做决定
nonisolated func decode(_ data: Data) -> Image { /* ... */ }

// App：自己决定在后台调用
@concurrent
func decodeInBackground(_ data: Data) async -> Image {
    decode(data)
}

3.5并发线程池

工作被卸载到后台后，由系统负责调度到某条后台线程上。并发线程池包含系统的全部后台线程，数量不定：Apple Watch 这类小设备可能只有一两条，核心更多的大设备线程也更多。任务跑在哪条后台线程上并不重要：任务挂起时，原线程会去运行其他就绪的任务；任务恢复时，可以在池中任意空闲线程上继续，不一定是它最初所在的那条。更多细节见视频推荐的 “Beyond the basics of structured concurrency”，以及本指南 §7.2 协作式线程池、Fig. 2。

04

跨线程共享数据：Sendable

有了并发，数据就会在线程之间流动。在 main actor 和并发线程池之间每来回一次，就是一次跨线程共享：URL 从 UI 传到后台去下载，下载得到的 Data 交给解码，解码得到的 image 连同 self 再回到 main actor。共享可变状态是出了名的易错，Swift 会在编译期就把这类错误找出来。

4.1值类型：其实没有在“共享”

URL 是值类型。复制到后台线程时，后台拿到的是一份独立副本；用户在 UI 上输入新 URL，主线程随意修改自己的副本，后台那份不受影响。字符串、整数、日期这些基础类型都是值类型；元素为值类型的数组、字典也是；只存值类型的 struct 和 enum（比如 Post）同样如此。

4.2什么是 Sendable

总能安全并发共享的类型叫 Sendable。它是一个协议，遵循它的类型可以安全共享：

  • Array 等集合是条件遵循：元素是 Sendable，集合就是 Sendable。
  • struct 和 enum 的所有实例数据都是 Sendable 时，可以标为 Sendable。
  • main actor 类型隐式就是 Sendable，不用显式声明。
  • actor（包括 main actor）通过“同一时刻只允许一个任务访问”来保护非 Sendable 状态。值传入或传出 actor 时，编译器都会检查它能否安全地交给并发代码。

以 await decodeImage(data) 为例：有两个值被送出 main actor，一个结果被送回来。

值方向为什么安全
self（ImageModel）送出main actor 类，可变状态由 main actor 保护，传引用到后台是安全的
data（Data）送出值类型，Sendable
image（Image 类）送回非 Sendable，但它是在后台新建的，没有任何并发代码引用它，所以可以安全地交给 main actor

4.3数据竞争是怎么被拦下的

swift
func scaleAndDisplay(imageName: String) {
    let image = loadImage(imageName)
    Task { @concurrent in
        image.scaleImage(by: 0.5)   // 后台线程修改 image
    }
    view.displayImage(image)        // 主线程同时读取 image
    // ❌ 编译错误：并发任务捕获了 image，而 main actor 也在使用它
}

如果希望缩放效果显示在 UI 上，正确做法是等缩放完成再显示：把三个操作都放进同一个任务，保证顺序。displayImage 必须在 main actor 上运行，所以在并发任务里用 await 调用它。如果 scaleAndDisplay 本身可以是 async 的，连新任务都不用建：

swift
@concurrent
func scaleAndDisplay(imageName: String) async {
    let image = loadImage(imageName)
    image.scaleImage(by: 0.5)
    await view.displayImage(image)   // 送给 main actor 之前完成所有修改
    // image.applyAnotherEffect()    // ❌ 已送出，main actor 可能已缓存它
}

image 一旦送给 main actor，main actor 就可以保存它的引用（比如放进缓存）。之后再修改它，编译器会报“不安全的并发访问”。解决办法是在送出之前完成所有修改。

4.4模型类与闭包

  • 模型类一开始通常在 main actor 上，便于直接给 UI 展示。如果后来需要在后台处理，就把它们标为 nonisolated，但大概率不应该让它们 Sendable。你不希望一部分模型在主线程更新、另一部分在后台更新；保持非 Sendable 就能阻止这种并发修改。而且让类 Sendable 通常要用锁这类底层同步机制，反而更麻烦。
  • 闭包和类一样会制造共享状态。例如把一个缩放 image 的闭包传给 perform(afterDelay:)，闭包就捕获了 image 的另一个引用。只要闭包不被并发调用，这就是安全的。只有确实需要并发共享时，才把函数类型标为 Sendable。
小结

常见类型大多是 Sendable，可以在并发任务间自由共享。类和闭包可能带着可变状态，一次只在一个任务里用它们。对象可以从一个任务送到另一个任务，但要在送出前完成全部修改。

05

actor：把数据移出主线程

App 越长越大，main actor 上的状态也越来越多。新加的子系统，比如管理网络访问的 network manager，会把“当前打开的连接”这类状态也放在 main actor 上。于是原本想在后台运行的 fetch-and-display 任务，不得不频繁跳回主线程去读这些数据。单个操作也许很快，但许多任务同时这样做就会形成争用（contention），累积成 UI 卡顿（切到 Fig. W1 的 ③′ 看看）。

之前用 @concurrent 把代码移出主线程；这一次要移出的是数据，所以引入自己的 actor：

swift
actor NetworkManager {
    var openConnections: [URL: Connection] = [:]

    func openConnection(for url: URL) async -> Connection {
        if let connection = openConnections[url] { return connection }
        let connection = Connection(url: url)
        openConnections[url] = connection
        return connection
    }
}
main actor自定义 actor
隔离数据，同一时刻只有一条线程访问✓✓
Sendable，可以自由传递引用✓✓
实例数量全局唯一任意多个，彼此独立
绑定线程主线程不绑定，在后台线程上运行

5.1什么时候用 actor，什么时候不用

  • 用：发现把数据放在 main actor 上导致太多代码在主线程上运行时，把某个非 UI 部分的数据（例如网络管理）拆进一个新 actor。
  • 不用：App 里大多数类都不该是 actor。面向 UI 的类应留在 main actor 上，以便直接操作 UI 状态。
  • 不用：模型类一般和 UI 一起放在 main actor 上，或者保持非 Sendable，避免鼓励对模型的大量并发访问。

5.1跨越隔离边界

值会通过两种方式跨越隔离域：异步调用，或者被闭包捕获。第一条警告来自 ContentView 里的 await 调用：它把绑定在 MainActor 上的 self.store 送进了另一个隔离域。作者没有给 TheMetStore 单独加 @MainActor，而是在 Build Settings 里把 Default Actor Isolation 设为 MainActor，让整个模块默认在主 actor 上。

5.2Sendable 类型

  • 值类型是 Sendable 的，因为传递的是副本。
  • 引用类型只有在没有可变状态、且所有不可变属性都是 Sendable 时才能是 Sendable；编译器只对 final 类做这项验证。
  • 全局函数、闭包、getter 和 setter 默认是 @Sendable 的。

第二条警告来自 fetchObjects(for:) 里的 await MainActor.run { objects.append(object) }：这个 @Sendable 闭包捕获了非 Sendable 的 TheMetStore。默认隔离改成 MainActor 之后，整个方法已经在主线程上，直接删掉 MainActor.run 包装即可。

5.3协议：隔离的遵循（isolated conformance）

swift.org 的说明是：协议遵循可能隐式影响隔离，取决于它是怎么声明的。默认隔离改成 MainActor 后，Object 和 ObjectIDs 都变成了 MainActor 隔离，但 Codable 的要求是非隔离的，于是两者冲突。Xcode 给出两个 Fix-it：

Fix-it效果教程选择
Isolate this conformance to the main actor with @MainActor遵循本身隔离到主 actor，只能在主 actor 上使用这份 Codable 实现✓ 采用
Turn data races into runtime errors with @preconcurrency压下编译期检查，改成运行时检测未采用
swift
struct Object: @MainActor Codable, Hashable { /* ... */ }
struct ObjectIDs: @MainActor Codable { /* ... */ }

隔离的协议遵循是 Swift 6.2 的新能力（SE-0470），配合 InferIsolatedConformances 时，MainActor 类型的遵循会被自动推断为隔离的。

重新编译运行后，Store 和 Service 的方法都跑在主线程上，只有 URLSession 的调用不在主线程。对这个 App 来说这正合适。

加入并发：@concurrent

为了演示真正需要后台执行的工作，教程加了一个模拟的慢操作 SlowProcess：用 Task.sleep(for:) 假装耗时，并在前后打印线程；TheMetService.getObject(from:) 在返回藏品之前调用它。

问题是，在 MainActor 默认隔离下，SlowProcess 也继承了 MainActor 隔离，doSomething 会在主线程上运行，可能卡住 UI。修法分两步：

  1. 把 SlowProcess 标为 nonisolated，让它脱离 MainActor。
  2. 把 doSomething 标为 @concurrent，让它总是在后台线程上运行。
swift
nonisolated struct SlowProcess {
    @concurrent func doSomething() async throws {
        print("doSomething start:", Thread.currentThread)
        try await Task.sleep(for: .seconds(1))   // 模拟耗时工作
        print("doSomething end:", Thread.currentThread)
    }
}

// TheMetService.getObject(from:) 中
try await SlowProcess().doSomething()
return object

只写 nonisolated 不够：在 Approachable Concurrency 下，nonisolated 的 async 函数会留在调用方的 actor 上（这里是主 actor）。要强制切到后台，必须用 @concurrent。

SE-0466：Main actor all the things!

App、脚本、命令行工具大多数代码都是在 main actor 上顺序执行的：除非你主动引入并发（比如创建一个 Task），一切都是顺序运行的。这种情况下根本不可能发生数据竞争，所以编译器给出的并发警告基本都是误报。SE-0466 新增一个编译器设置，让模块内的声明默认推断为 @MainActor，新手也不用过早接触并发概念。

这是源码不兼容的改动，存量项目需要主动开启：

swift
// 编译器参数
// -default-isolation MainActor

// Package.swift
.target(
    name: "MyApp",
    swiftSettings: [
        .defaultIsolation(MainActor.self)
    ]
)

后来 Xcode 26 把它做成了 Build Settings 里的 Default Actor Isolation，新建的 App 项目默认就是 MainActor。

04

SE-0461：nonisolated async 函数在调用方 actor 上运行

作者指出，编译器当时对 nonisolated 的同步方法和异步方法处理不一致：同步方法在调用方所在的线程上执行，异步方法却会切到全局并发执行器（后台线程）。这很让人困惑，SE-0461 就是为了统一这一点。

4.1文中的例子

swift
class NotSendable {
    func performAsync() async {
        print("Task started on thread: \(Thread.currentThread)")
        // Old situation: Task started on thread: <NSThread: 0x600003694d00>{number = 8, name = (null)}
        // New situation: Task started on thread: <_NSMainThread: 0x6000006b4040>{number = 1, name = main}
    }
}

@MainActor
struct NewThreadingDemonstrator {

    func demonstrate() async {
        print("Starting on the main thread: \(Thread.currentThread)")
        // Prints: Starting on the main thread: <_NSMainThread: 0x6000006b4040>{number = 1, name = main}

        let notSendable = NotSendable()
        await notSendable.performAsync()

        /// Returning on the main thread.
        print("Resuming on the main thread: \(Thread.currentThread)")
        // Prints: Resuming on the main thread: <_NSMainThread: 0x6000006b4040>{number = 1, name = main}
    }
}

打印线程用的是和 Kodeco 教程相同的绕法：

swift
extension Thread {
    /// A convenience method to print out the current thread from an async method.
    /// This is a workaround for compiler error:
    /// Class property 'current' is unavailable from asynchronous contexts; Thread.current cannot be used from async contexts.
    public static var currentThread: Thread {
        return Thread.current
    }
}

4.2这个 Thread 扩展在做什么

它只有一个作用：绕过编译器的限制，让 async 函数里也能拿到当前线程，方便打印调试。

为什么 async 函数里不能直接用 Thread.current

Thread.current 被标记为在 async 上下文中不可用，大致相当于：

swift
@available(*, noasync, message: "Thread.current cannot be used from async contexts.")
class var current: Thread { get }

func performAsync() async {
    print(Thread.current)
    // ❌ Class property 'current' is unavailable from asynchronous contexts
}

原因是 async 函数每遇到一个 await 就可能挂起，恢复时可能换了一条线程。依赖“当前线程”的代码，比如线程局部存储、按线程判断身份、在一个线程加锁另一个线程解锁，在 async 代码里都会出隐蔽的 bug。所以 Swift 干脆不让直接用，引导你用 actor 隔离而不是线程来思考。

swift
func work() async {
    let t1 = Thread.current   // 假设是线程 5
    await something()         // 挂起
    let t2 = Thread.current   // 可能已经是线程 8
}

为什么包一层就能绕过去

noasync 检查是语法层面的，只看调用写在哪里。currentThread 的 getter 是普通同步代码，在里面调用 Thread.current 合法；currentThread 自己没有被标记 noasync，所以 async 函数可以调用它。

调用位置Thread.currentThread.currentThread
直接写在 async 函数里✗ 报错✓ 允许
写在同步 getter 里✓ 允许—
  • extension Thread：给 Foundation 的 Thread 类加成员。
  • static var currentThread: Thread { … }：类型级的只读计算属性，用法 Thread.currentThread，和 Thread.current 一样。
  • public：对这个例子无关紧要，只是让别的模块也能用。

拿到的值可信吗

在调用的那一瞬间是准确的：getter 同步执行，中间没有挂起点，返回的就是此刻运行这段代码的线程。所以拿来打印“这一行跑在哪条线程上”没问题。但它不保证下一行还是这条线程，过了一个 await 就可能变。只适合调试和日志，不要写进业务逻辑。

坑：默认 MainActor 隔离下要加 nonisolated

模块开了 Default Actor Isolation = MainActor 时，不加修饰的扩展会被推断为 @MainActor。读这个属性要先跳到主线程，于是测出来永远是主线程，完全失去意义。Kodeco 教程写成 nonisolated extension Thread 就是这个原因：加上 nonisolated 后，getter 在调用方当前所在的线程上执行，测到的才是真实情况。SwiftLee 的例子没开默认 MainActor，所以不加也没问题。

swift
// ✗ 默认 MainActor 隔离下被推断为 @MainActor
extension Thread {
    static var currentThread: Thread { Thread.current }
}

@concurrent func work() async {
    print(await Thread.currentThread)   // 先切到主线程才能读 → 永远打印主线程
}

// ✓ 两种设置下都测得准
nonisolated extension Thread {
    static var currentThread: Thread { Thread.current }
}

只想确认在不在主 actor 上？

更推荐用隔离相关的 API，而不是看线程。另外 Thread.isMainThread 同样被标记了 noasync，本站的实验也是用同样的办法包了一层 Thread.isMain。

swift
MainActor.assertIsolated()        // 不在 MainActor 上就崩溃（Debug）
MainActor.preconditionIsolated()  // Release 下也检查
print(#isolation)                 // 当前隔离：MainActor / 某个 actor / nil

4.3例子里没写 nonisolated，为什么说它是 nonisolated？

func performAsync() async 确实没有写 nonisolated 关键字。一个声明属于哪个隔离域，按下面的顺序判断，先命中的为准：

  1. 有显式标注（@MainActor、nonisolated、@concurrent…）就按标注来。
    performAsync：没有标注 → 继续
  2. 所在类型有隔离（actor、@MainActor class…）就继承类型的隔离。
    NotSendable：普通 class，没有隔离 → 继续
  3. 看模块的默认隔离：swift.org 默认是 nonisolated；开了 SE-0466 / Xcode 26 新项目则是 MainActor。
    文章的环境是默认值 → performAsync 隐式 nonisolated

所以文中的 performAsync() 和显式写成 nonisolated func performAsync() async 完全等价。反过来：如果模块开了默认 MainActor 隔离，同一行声明会被推断成 @MainActor，不管 SE-0461 开没开都在主线程上运行（见下图 D）。
