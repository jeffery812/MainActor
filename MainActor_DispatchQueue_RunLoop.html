关键关系：

  • 主线程上跑着 RunLoop.main；DispatchQueue.main 的任务由主 RunLoop 排空执行；MainActor 的执行器底层就是提交到主队列。
  • DispatchQueue.global() 和自定义队列由 GCD 管理的线程池执行，GCD 会在线程阻塞时额外创建线程。
  • Swift Concurrency 中非主 actor 的任务跑在协作式线程池（cooperative thread pool）上，线程数 ≈ CPU 核心数，不会因为阻塞而补充线程。
  • OperationQueue 是对 GCD 的面向对象封装，增加了依赖、取消、并发数控制。
1

基础概念

概念含义
进程 / 线程线程是 CPU 调度的基本单位。iOS App 有一个主线程（UI 线程）和若干后台线程。
队列（Queue）GCD 的任务容器，FIFO。开发者面向队列而不是线程编程，由系统决定使用哪个线程。
任务（Task）Swift Concurrency 中的异步工作单元，可以挂起、恢复，可能在不同线程上恢复。
串行 vs 并发串行：同一时刻只执行一个任务。并发：可同时执行多个任务。
同步 vs 异步同步（sync）：调用方等待任务完成。异步（async）：提交后立即返回。
并发 vs 并行并发是结构（多个任务交替推进）；并行是执行（多个核心同时执行）。
阻塞 vs 挂起阻塞（block）：线程卡住什么也不做，占着线程。挂起（suspend，await）：任务让出线程，线程可以去执行其他任务。
数据竞争（Data Race）多个线程同时访问同一内存且至少一个是写，没有同步。Swift 6 在编译期消除。
竞态条件（Race Condition）结果依赖于执行时序的逻辑错误。即使没有数据竞争也可能发生（如 actor 重入）。
QoS / 优先级告诉系统任务的重要程度，影响调度与能耗。
2

Thread

2.1是什么

Thread（NSThread）是对 POSIX 线程的封装，是最底层的多线程方式。

swift
let thread = Thread {
    print("在新线程中：\(Thread.current)")
}
thread.name = "com.example.worker"
thread.qualityOfService = .utility
thread.start()

Thread.isMainThread          // 当前是否主线程
Thread.sleep(forTimeInterval: 1)   // 阻塞当前线程

2.2何时使用

  • 几乎不需要在 App 代码中直接使用。
  • 极少数场景：需要一个长期存在、带自己 RunLoop 的线程（例如某些旧的网络库、需要专用线程的 C 库）。

2.3注意

  • 在 Swift Concurrency 的 async 函数中，Thread.current 已被标为不可用（Swift 6），因为任务在 await 前后可能运行在不同线程上，"当前线程"不再有意义。判断主线程隔离应使用 MainActor.assumeIsolated / MainActor.preconditionIsolated()。

2.4Thread 的闭包在哪个线程执行？

以 2.1 的代码为例，要把创建 Thread 对象和执行闭包分开看：

swift
let thread = Thread {                          // ① 创建 Thread 对象
    print("在新线程中：\(Thread.current)")      // ② 闭包：新线程的入口
}
thread.start()                                 // ③ 启动
步骤在哪个线程执行说明
① let thread = Thread { ... }当前线程（写在按钮回调 / onAppear 里就是主线程）只是在内存里创建一个 Thread 对象（“线程的描述”）。此时新线程还不存在，闭包也不会执行
② 闭包体新创建的后台线程start() 之后系统才创建一条新的 POSIX 线程，并在其上执行闭包
③ thread.start()当前线程异步：立即返回，不等闭包执行完。不调用 start()，闭包永远不会执行

所以在闭包里：

swift
Thread.isMainThread   // false
Thread.current        // <NSThread: 0x600001234567>{number = 8, name = (null)}

// 对比：在主线程打印 Thread.current
// <_NSMainThread: 0x...>{number = 1, name = main}
主线程创建 Thread 对象→start()→继续往下执行（不等待） 新线程执行闭包 print(...)→结束、线程退出
  • 闭包结束，线程就退出。想让它长期存在，需要在闭包里运行它自己的 RunLoop（即 2.2 所说的“长期存在、带自己 RunLoop 的线程”）。
  • 直接调用 thread.main() 不会开新线程：闭包会在当前线程上同步执行，和普通函数调用一样。开新线程只能用 start()。
  • 执行顺序不确定：start() 之后的主线程代码，可能比闭包里的 print 先输出。
3

RunLoop

3.1是什么

RunLoop 是线程的事件处理循环："等待事件 → 处理事件 → 休眠"。每个线程最多一个 RunLoop，只有主线程的 RunLoop 默认在运行（由 UIApplicationMain / SwiftUI App 启动）。

关键概念是 Mode（模式）：

Mode说明
.default默认模式，空闲时处于此模式
.tracking（UITrackingRunLoopMode）用户拖动/滚动 ScrollView 时切换到此模式
.common伪模式，一个"集合"，默认包含 .default 和 .tracking

一个输入源（如 Timer）只会在它被注册的模式下触发。

3.2典型场景

swift
// 1) SwiftUI 中的定时器
struct CountdownView: View {
    @State private var remaining = 60
    // in: .common —— 滚动时也继续触发（若用 .default，滚动时会暂停）
    private let timer = Timer.publish(every: 1, on: .main, in: .common).autoconnect()

    var body: some View {
        Text("\(remaining)")
            .onReceive(timer) { _ in
                if remaining > 0 { remaining -= 1 }
            }
    }
}

// 2) Combine 切换到 RunLoop.main —— 在 .default 模式执行，滚动时会被推迟
imagePublisher
    .receive(on: RunLoop.main)
    .sink { self.thumbnail = $0 }

// 3) 在指定 mode 下于下一次 RunLoop 迭代执行
RunLoop.main.perform(inModes: [.common]) { /* ... */ }

// 4) CADisplayLink（逐帧回调）
let link = CADisplayLink(target: self, selector: #selector(step))
link.add(to: .main, forMode: .common)

3.3特点

  • 最底层，没有编译期检查。
  • 与滚动强相关：注册在 .default 的任务在滚动时不执行。
  • 用于 Timer、DisplayLink、端口、perform(_:with:afterDelay:) 等依赖 RunLoop 的 API。
4

GCD（Grand Central Dispatch）

GCD 的核心思想：把任务（block）提交给队列，由系统管理线程池执行。

4.1三种队列

队列类型执行线程用途
DispatchQueue.main串行主线程UI 更新
DispatchQueue.global(qos:)并发（系统共享）线程池中的后台线程一次性的后台工作
DispatchQueue(label:)串行（默认）线程池中的后台线程保护共享状态、按顺序执行
DispatchQueue(label:, attributes: .concurrent)并发（私有）线程池中的后台线程读写锁（配合 barrier）

4.2DispatchQueue.main

swift
// 旧式回调切回主线程
URLSession.shared.dataTask(with: url) { data, _, _ in
    let image = data.flatMap(UIImage.init(data:))
    DispatchQueue.main.async { self.image = image }
}.resume()

// 延迟执行
DispatchQueue.main.asyncAfter(deadline: .now() + 2) { showToast = false }

// 推迟到下一轮 RunLoop（例如 onAppear 后设置焦点）
.onAppear { DispatchQueue.main.async { isFocused = true } }
  • async 总是入队，等当前代码执行完之后才执行。
  • 主队列由主 RunLoop 在 common modes 下排空，所以滚动期间也会执行。
  • 在主线程调用 DispatchQueue.main.sync → 死锁。
  • Swift 6 编译器会把传给 DispatchQueue.main.async 的闭包视为 @MainActor 隔离，可直接访问主 actor 状态。

4.3DispatchQueue.global(qos:)

系统提供的共享并发队列，按 QoS 区分：

QoS场景对应 TaskPriority
.userInteractive动画、事件处理，需立即完成— （主线程级别）
.userInitiated用户点击后等待的结果（打开文档）.userInitiated / .high
.default默认值，global() 不传参时使用.medium
.utility有进度条的长任务（下载、导入）.utility / .low
.background用户感知不到的任务（备份、索引、预取）.background
swift
DispatchQueue.global(qos: .userInitiated).async {
    let thumbnail = makeThumbnail(from: data)       // 耗时工作
    DispatchQueue.main.async {
        self.thumbnail = thumbnail                  // 回到主线程更新 UI
    }
}

注意：

  • global 队列是所有人共享的，不能用 barrier（在 global 队列上 barrier 等同普通 async），也不适合用来保护状态。
  • 不要在 global 队列上大量提交会阻塞的任务——GCD 会为被阻塞的线程补充新线程，导致线程爆炸（thread explosion，上限约 64 个），引起内存与调度开销，甚至死锁。

4.4自定义串行队列：保护共享状态

swift
final class Cache: @unchecked Sendable {
    private var storage: [String: Data] = [:]
    private let queue = DispatchQueue(label: "com.example.cache")   // 串行

    func value(for key: String) -> Data? {
        queue.sync { storage[key] }
    }

    func set(_ data: Data, for key: String) {
        queue.async { self.storage[key] = data }
    }
}

在 Swift Concurrency 中，这种模式通常由 actor 或 Mutex 取代。

4.5并发队列 + barrier：读写锁

swift
final class ThreadSafeDictionary<Key: Hashable, Value>: @unchecked Sendable {
    private var dict: [Key: Value] = [:]
    private let queue = DispatchQueue(label: "rw", attributes: .concurrent)

    subscript(key: Key) -> Value? {
        get { queue.sync { dict[key] } }                       // 多个读可并发
        set { queue.async(flags: .barrier) { self.dict[key] = newValue } }  // 写独占
    }
}

4.6DispatchGroup：等待一组任务完成

swift
let group = DispatchGroup()
var results: [Data] = []
let lock = NSLock()

for url in urls {
    group.enter()
    URLSession.shared.dataTask(with: url) { data, _, _ in
        if let data { lock.withLock { results.append(data) } }
        group.leave()
    }.resume()
}

group.notify(queue: .main) {
    print("全部完成：\(results.count)")
}
// group.wait() 会阻塞当前线程，切勿在主线程调用

Swift Concurrency 对应：withTaskGroup / async let。

4.7DispatchSemaphore：限制并发数 / 同步等待

swift
let semaphore = DispatchSemaphore(value: 3)       // 最多 3 个并发
for item in items {
    DispatchQueue.global().async {
        semaphore.wait()
        defer { semaphore.signal() }
        process(item)
    }
}

⚠ 绝不能在 Swift Concurrency 的 async 上下文中使用 semaphore.wait()：协作式线程池线程数有限，阻塞会导致整个池子饿死甚至死锁。

4.8DispatchWorkItem：可取消的任务（如防抖）

swift
private var searchWorkItem: DispatchWorkItem?

func search(_ text: String) {
    searchWorkItem?.cancel()
    let item = DispatchWorkItem { [weak self] in self?.performSearch(text) }
    searchWorkItem = item
    DispatchQueue.main.asyncAfter(deadline: .now() + 0.3, execute: item)
}

cancel() 只能阻止尚未开始的 work item 执行；已经在跑的需要自己检查 item.isCancelled。

4.9DispatchSource：系统事件 / 高精度定时器

swift
let timer = DispatchSource.makeTimerSource(queue: .global(qos: .utility))
timer.schedule(deadline: .now(), repeating: .seconds(1))
timer.setEventHandler { print("tick") }
timer.resume()
// 不依赖 RunLoop，滚动时也照常触发；需持有 timer 引用，否则会被释放

还可监听文件变化（makeFileSystemObjectSource）、进程信号、内存压力等。

4.10DispatchQueue.concurrentPerform：并行循环

swift
DispatchQueue.concurrentPerform(iterations: images.count) { index in
    thumbnails[index] = resize(images[index])   // 需要保证写入线程安全
}
// 同步调用：所有迭代完成后才返回；会自动按 CPU 核心数并行

4.11sync vs async 小结

syncasync
调用方阻塞等待 block 执行完立即返回
常见用途从串行队列安全读取值提交工作
风险对当前所在的串行队列 sync → 死锁捕获 self 可能延长生命周期
5

OperationQueue

5.1是什么

基于 GCD 的面向对象封装。相比 GCD 多了：依赖关系、取消、最大并发数、KVO 状态观察、暂停/恢复。

swift
let queue = OperationQueue()
queue.maxConcurrentOperationCount = 2          // 1 即串行队列
queue.qualityOfService = .utility

let download = BlockOperation { downloadFile() }
let unzip    = BlockOperation { unzipFile() }
let save     = BlockOperation { saveToDB() }

unzip.addDependency(download)                  // 依赖：download 完成后才执行 unzip
save.addDependency(unzip)

queue.addOperations([download, unzip, save], waitUntilFinished: false)

OperationQueue.main.addOperation { updateUI() } // 主队列

queue.cancelAllOperations()                    // 取消（已在运行的需自行检查 isCancelled）
queue.isSuspended = true                       // 暂停调度新的 operation

5.2何时使用

  • 有复杂依赖图、需要取消/暂停、需要限制并发数的任务（如批量下载、图片处理流水线）。
  • 新代码中，大多数场景可以用 TaskGroup + 结构化并发替代；但需要"暂停整个队列""运行时修改并发数"时，OperationQueue 仍然方便。
6

Swift Concurrency

Swift 5.5 引入、Swift 6 强制数据竞争安全的语言级并发模型。核心理念：结构化并发 + actor 隔离 + 编译期检查。

6.1async / await

swift
func fetchUser(id: Int) async throws -> User {
    let (data, _) = try await URLSession.shared.data(from: url(for: id))
    return try JSONDecoder().decode(User.self, from: data)
}
  • await 是潜在挂起点：任务让出线程，等结果返回后再恢复，恢复时可能在另一个线程（但会回到正确的 actor 上）。
  • 挂起不会阻塞线程，因此主线程上 await 不会卡 UI。

6.2协作式线程池（Cooperative Thread Pool）

  • 非主 actor 的任务默认跑在全局并发执行器上，底层是一个线程数 ≈ CPU 核心数的线程池。
  • 每个线程依靠任务在 await 处主动让出来切换工作（"协作式"）。
  • 前进保证（forward progress）：任务不能无限期阻塞线程。因此在 async 代码中禁止：semaphore.wait()、group.wait()、Thread.sleep、长时间同步 I/O、DispatchQueue.sync 到可能等待异步任务的队列等。
  • 对比 GCD：GCD 在线程阻塞时会补充线程（可能线程爆炸）；协作池不会补充线程（阻塞会饿死）。

6.3Task：非结构化任务

swift
// 从同步上下文进入异步世界
Button("刷新") {
    Task { await viewModel.refresh() }
}

// 保存句柄以便取消或获取结果
let task = Task(priority: .userInitiated) { () -> [Item] in
    try await api.fetchItems()
}
let items = try await task.value
task.cancel()

Task { } 继承调用方的：

继承项说明
actor 隔离在 @MainActor 方法里创建 → 闭包在 MainActor 上运行
优先级继承当前任务优先级
TaskLocal 值继承
取消状态不继承——父任务被取消，Task {} 不会自动取消（非结构化）

⚠ 常见误区：在 @MainActor 上下文中 Task { heavyCPUWork() }，同步的 heavyCPUWork() 仍在主线程执行，会卡 UI。

6.4Task.detached：脱离上下文的任务

swift
Task.detached(priority: .background) {
    // 不继承 actor、优先级、TaskLocal
    let report = await generateReport()
    await MainActor.run { self.report = report }
}
  • 不继承任何上下文，运行在全局并发执行器上。
  • 适合：确实需要与当前 actor 完全无关的后台工作。
  • 官方建议优先使用结构化并发或 nonisolated/@concurrent 函数，Task.detached 是最后手段。

6.5Task.immediate（Swift 6.2，iOS 26+）

swift
Task.immediate { @MainActor in
    isLoading = true           // 同步立即执行，不等待下一轮调度
    await load()               // 第一个挂起点之后才变成普通异步任务
}
  • 普通 Task {} 总是入队，稍后执行；Task.immediate 会在当前线程立即同步执行，直到第一个真正的挂起点。
  • 适合需要"立刻在当前 actor 上更新状态"的场景，避免一帧的延迟。

6.6async let：并行的固定数量子任务（结构化）

swift
func loadDashboard() async throws -> Dashboard {
    async let user    = api.fetchUser()
    async let orders  = api.fetchOrders()
    async let notices = api.fetchNotices()
    // 三个请求并行执行
    return try await Dashboard(user: user, orders: orders, notices: notices)
}
  • 是子任务：作用域结束前必须完成；若作用域提前退出（如抛错），未 await 的子任务会被自动取消并等待。
  • 适合数量在编译期已知的并行操作。

6.7TaskGroup：动态数量的子任务（结构化）

swift
func downloadAll(_ urls: [URL]) async throws -> [URL: Data] {
    try await withThrowingTaskGroup(of: (URL, Data).self) { group in
        for url in urls {
            group.addTask {
                let (data, _) = try await URLSession.shared.data(from: url)
                return (url, data)
            }
        }
        var result: [URL: Data] = [:]
        for try await (url, data) in group {    // 按完成顺序收集
            result[url] = data
        }
        return result
    }
}

限制并发数（替代 Semaphore）：

swift
await withTaskGroup(of: Void.self) { group in
    let maxConcurrent = 3
    var iterator = items.makeIterator()

    for _ in 0..<maxConcurrent {
        guard let item = iterator.next() else { break }
        group.addTask { await process(item) }
    }
    while await group.next() != nil {
        if let item = iterator.next() {
            group.addTask { await process(item) }
        }
    }
}
变体说明
withTaskGroup子任务不抛错
withThrowingTaskGroup子任务可抛错；任一错误被抛出时，其余子任务被取消
withDiscardingTaskGroup（iOS 17+）不收集结果，子任务完成后立即释放，适合长期运行的"服务器循环"

6.8取消（Cancellation）

Swift 的取消是协作式的：cancel() 只是设置一个标志，任务需要自己检查。

swift
func processAll(_ items: [Item]) async throws {
    for item in items {
        try Task.checkCancellation()             // 已取消则抛 CancellationError
        // 或：if Task.isCancelled { return }
        await process(item)
    }
}

// 取消时需要立即执行清理（如取消底层回调式请求）
try await withTaskCancellationHandler {
    try await legacyDownload()
} onCancel: {
    legacyRequest.cancel()                       // 可能在任意线程被调用
}
  • 结构化子任务（async let、TaskGroup）会随父任务一起取消。
  • URLSession.data(from:)、Task.sleep 等系统 API 会自动响应取消。
  • SwiftUI 的 .task {} 在视图消失时自动取消。

6.9优先级与睡眠/让出

swift
Task(priority: .background) { ... }
Task.currentPriority

try await Task.sleep(for: .seconds(1))   // 挂起，不阻塞线程；会响应取消
await Task.yield()                        // 主动让出，给其他任务执行机会（长 CPU 循环中使用）

TaskPriority：.high(= .userInitiated)、.medium、.low(= .utility)、.background。系统会做优先级提升（priority escalation）：高优先级任务等待低优先级任务时，后者会被提升。

6.10TaskLocal：任务级"上下文变量"

swift
enum RequestContext {
    @TaskLocal static var traceID: String = "none"
}

await RequestContext.$traceID.withValue("abc-123") {
    await handle()           // handle 及其子任务（含 Task {}）都能读到 "abc-123"
}

类似线程局部存储，但绑定在任务树上。适合日志追踪 ID 等。

6.11actor：保护可变状态

swift
actor ImageCache {
    private var cache: [URL: UIImage] = [:]

    func image(for url: URL) -> UIImage? { cache[url] }

    func load(_ url: URL) async throws -> UIImage {
        if let cached = cache[url] { return cached }
        let (data, _) = try await URLSession.shared.data(from: url)
        let image = UIImage(data: data)!
        cache[url] = image                       // ⚠️ 见下方"重入"
        return image
    }
}

let image = try await cache.load(url)            // 外部访问必须 await
  • actor 保证同一时间只有一个任务在访问其内部状态（串行执行），从而消除数据竞争。
  • 可重入（reentrancy）：在 await 处，actor 可以去执行其他调用。所以 await 之后，之前读取的状态可能已经变化。上例中两个并发调用会重复下载同一 URL；解决方式是缓存"进行中的 Task"：
swift
actor ImageLoader {
    private var tasks: [URL: Task<UIImage, Error>] = [:]

    func load(_ url: URL) async throws -> UIImage {
        if let existing = tasks[url] { return try await existing.value }
        let task = Task { try await download(url) }
        tasks[url] = task
        return try await task.value
    }
}
  • nonisolated：标记不访问隔离状态的成员，可在外部同步调用。
  • isolated 参数：func f(_ a: isolated MyActor) 让函数运行在参数 actor 上。
  • #isolation：获取调用方的隔离，常用于 isolation: isolated (any Actor)? = #isolation 参数，让通用 async 函数在调用方的 actor 上执行。

6.12MainActor 与全局 actor

@MainActor 是一个全局 actor，其执行器即主线程/主队列。被标注的类型、函数、属性、闭包都被隔离到主线程。

swift
@MainActor
@Observable
final class ProfileViewModel {
    var user: User?
    var isLoading = false

    func load() async {
        isLoading = true
        defer { isLoading = false }
        user = try? await api.fetchUser()   // 后台执行，返回后自动回到 MainActor
    }
}

切换到主 actor 的几种方式：

swift
await MainActor.run { self.title = "Done" }   // 在主 actor 上执行一个闭包
Task { @MainActor in model.refresh() }        // 新建一个主 actor 任务（总是入队）
MainActor.assumeIsolated { model.update() }   // 断言已在主线程（不在则崩溃），用于旧回调

SwiftUI 相关：

  • View 协议整体是 @MainActor（iOS 18 SDK 起；之前仅 body）。
  • .task {} 闭包继承 View 的隔离，即在 MainActor 上运行。

自定义全局 actor：

swift
@globalActor
actor DatabaseActor {
    static let shared = DatabaseActor()
}

@DatabaseActor
final class DatabaseStore {
    func save(_ item: Item) { ... }     // 所有成员都串行在 DatabaseActor 上
}

适合：把一组分散在多个类型中的操作统一到同一个串行隔离域。

6.13Sendable：跨隔离域传值的安全标记

  • Sendable 表示值可以安全地在并发域之间传递。
    • 值类型（成员都是 Sendable 的 struct/enum）自动满足。
    • final class 且所有属性为 let 且是 Sendable → 可声明 Sendable。
    • actor 天然 Sendable。
    • 内部用锁保护的 class → @unchecked Sendable（开发者自行保证）。
  • @Sendable 闭包：不能捕获可变的非 Sendable 状态。
  • sending 参数/返回值（Swift 6）：表示值的所有权被"转移"到另一个隔离域，转移后调用方不能再使用，从而允许传递非 Sendable 值。

6.14Continuation：桥接回调式 API

swift
func fetchLocation() async throws -> CLLocation {
    try await withCheckedThrowingContinuation { continuation in
        legacyLocationManager.requestLocation { result in
            switch result {
            case .success(let location): continuation.resume(returning: location)
            case .failure(let error):    continuation.resume(throwing: error)
            }
        }
    }
}
  • 规则：必须且只能 resume 一次。Checked 版本会在违反时给出运行时警告/崩溃；Unsafe 版本无检查、性能略好。

6.15AsyncSequence / AsyncStream：异步序列

swift
// 消费
for try await line in url.lines { print(line) }
for await notification in NotificationCenter.default.notifications(named: .NSCalendarDayChanged) { ... }

// 把回调/委托转为 AsyncStream
func locationUpdates() -> AsyncStream<CLLocation> {
    AsyncStream { continuation in
        let delegate = LocationDelegate { continuation.yield($0) }
        continuation.onTermination = { _ in delegate.stop() }
        delegate.start()
    }
}

// iOS 17+ 便捷构造
let (stream, continuation) = AsyncStream.makeStream(of: Int.self)
  • 是 Combine Publisher 在 Swift Concurrency 中的对应物（拉取式 vs 推送式）。
  • for await 循环会随任务取消而结束。

6.16Executor（执行器）

  • 每个 actor 有一个串行执行器；MainActor 的执行器绑定主线程。
  • 非隔离的 async 代码运行在全局并发执行器（协作池）上。
  • 高级特性：自定义 SerialExecutor（让 actor 跑在指定的 DispatchQueue 上，便于与旧代码共享队列）、TaskExecutor（SE-0417，Task(executorPreference:)）。一般 App 开发很少需要。

常见陷阱

  1. 在 @MainActor 里用 Task {} 跑 CPU 密集型工作 → 仍在主线程，卡 UI。改用 @concurrent / nonisolated 函数或 Task.detached。
  2. 在 async 上下文中阻塞（semaphore.wait()、group.wait()、Thread.sleep、DispatchQueue.sync 等待异步结果）→ 协作池饿死/死锁。
  3. 主线程 DispatchQueue.main.sync；或对当前所在的串行队列 sync → 死锁。
  4. GCD 线程爆炸：大量阻塞任务丢进 global 队列。
  5. actor 重入：await 之后假设状态没变 → 重复下载、状态错乱。await 后重新检查状态，或缓存进行中的 Task。
  6. 忘记取消：onAppear { Task { } } 不会随视图消失而取消；用 .task {}。保存的 Task 句柄在 deinit / onDisappear 中 cancel()。
  7. 非结构化任务的 self 强引用：Task { await self.longRunning() } 会让 self 存活到任务结束。长任务需配合取消或 [weak self]。
  8. Continuation 未 resume 或 resume 两次 → 任务永远挂起 / 崩溃。
  9. 从后台线程修改 @Published / @Observable 驱动 UI 的属性 → 运行时警告、UI 不一致。
  10. receive(on: RunLoop.main) 导致滚动时 UI 不更新；Timer 用了 .default mode 导致滚动时停表。
  11. 依赖各种"切到主线程"方式之间的执行顺序。
  12. @unchecked Sendable 滥用：只是让编译器闭嘴，不会让代码真正线程安全。
  13. global 队列上用 barrier：无效。

在 iPhone 17 Pro 模拟器（12 核 Mac）上实测的部分结果：

  • nonisolated(nonsending) 与 @concurrent：从 MainActor 调用时，前者在主线程执行，后者在后台线程执行。
  • 线程爆炸：100 个各阻塞 100ms 的任务，GCD 用了 36 个线程；TaskGroup 的协作式线程池只用了 12 个（等于核心数）。
  • 数据竞争：4 个线程 × 50,000 次 += 1，无保护结果只有 71,212（期望 200,000）；Atomic 15ms、Mutex 33ms、NSLock 45ms、actor 84ms、串行队列 sync 568ms。
  • actor 重入：朴素缓存下载 5 次，去重缓存下载 1 次。
  • await MainActor.run：在 MainActor 上调用时，之前排队的 Task { @MainActor } 先于 MainActor.run 的闭包执行。所以不要依赖调度顺序。
