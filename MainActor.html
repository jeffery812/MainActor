Support/ · build settings

13 个页面共用同一套基础设施。不先理解这几处，后面很多写法（满屏的 nonisolated、反复出现的 let console = console）都会显得莫名其妙。

编译设置决定了"默认在哪儿跑"

设置值对代码的影响
SWIFT_DEFAULT_ACTOR_ISOLATIONMainActor模块里没有标注的类型和函数都隐式是 @MainActor：所有 View、Console、TickModel、CombineAsyncLab 都在主线程。想让代码不在主线程，必须显式写 nonisolated。
SWIFT_APPROACHABLE_CONCURRENCYYES打开一组 upcoming feature，其中最关键的是 SE-0461：nonisolated async 函数默认变成 nonisolated(nonsending)，即在调用方的 actor 上执行。要真正切到后台，得写 @concurrent。
SWIFT_VERSION5.0用 Swift 6.2 编译器，但不启用 Swift 6 语言模式：并发问题多数是警告而非错误。所以 @unchecked Sendable、assumeIsolated 这类"告诉编译器我知道"的写法要格外小心，它们不会让代码变安全。

这三行是理解整个工程的钥匙。演示 #02 里 Task { 同步计算 } 会卡 UI，await nonsending 函数 也会卡 UI，根本原因都在这张表里。

Console：在"调用那一刻"记录线程

@Observable
final class Console {                       // 默认隔离 → @MainActor，因此隐式 Sendable
    private(set) var entries: [LogEntry] = []
    nonisolated let buffer = LogBuffer()     // Mutex 保护，任何线程可写

    nonisolated func log(_ message: String) {
        buffer.append(message)               // ← 同步读取 pthread_main_np / 线程号
        Task { @MainActor [weak self] in self?.refresh() }   // UI 刷新另外排队
    }
}
  • log 必须是 nonisolated 的同步函数。如果它是 @MainActor，后台代码调用时就得 await，切回主线程才执行，记下的线程永远是 main，实验也就没意义了。现在线程信息在调用方所在的线程上同步读取，看到的就是真实位置。
  • 记录和显示分开。LogBuffer 用 Mutex 串行化 append，所以日志的序号顺序就是真实执行顺序；UI 刷新则异步排到 MainActor 上，晚一点也不影响顺序。
  • 时间戳是相对 clear() 的。每个实验先 console.clear()，于是"耗时""谁先谁后"可以直接读出来。
  • Console 本身是 MainActor 隔离的类。全局 actor 隔离的类自动是 Sendable，所以它能被任何 @Sendable 闭包（Task.detached、GCD）捕获，这是后面所有实验能跨线程打日志的前提。

LogBuffer 为什么必须是 Sendable、state 为什么包在 Mutex 里、buffer 为什么要 nonisolated，见下一节 #00+ 深读。

Work：三种"耗时"，各有用途

Work.spin(seconds:)

CPU 忙等，占住当前线程并消耗 CPU。用来证明代码跑在哪：在主线程 spin，齿轮就停。#02、#06、#10 用它。

Work.block(milliseconds:)

usleep：不耗 CPU，但线程被占住。GCD 看到线程阻塞会补新线程，于是 #08 的"线程爆炸"能复现出来；spin 是 CPU 密集，演示不出这一点。

Task.sleep

挂起而非阻塞，线程会被让出去。#02 的对照组，#05、#11 模拟网络请求。被取消时会抛错，所以也是"能否被取消"的探针。

Work.spinNonsending 和 Work.spinConcurrent 函数体完全相同，只差一个属性，专门留给 #02 做对照。

其余小零件

  • DemoScreen / DemoButton：上半屏是说明和按钮，下半屏是日志。13 页布局一致，读者只需要关注按钮之间的差别。
  • RunningCounter、ThreadSet：Mutex 包着的 Sendable 小类，分别统计"同时运行数的峰值"和"用到过几个线程"。#08 用它们把并发度变成一个可以读的数字。
  • 实验代码放在 nonisolated enum 命名空间里（GCDExperiments、FakeAPI、Bridges、Probe……）。在默认 MainActor 隔离下，不加 nonisolated 的静态函数都属于主线程；把实验抽到非隔离命名空间，被测代码才不会被"默认值"悄悄绑在主线程上，也能从后台闭包里直接调用。

C1直接写 console 有什么问题？

闭包里写 console，实际是 self.console。闭包捕获的是整个 View，等闭包真正运行时才去调用 console 的 getter 取值。

  • 这个 getter 属于 MainActor。@State 是属性包装器，console 其实是一个计算属性（wrappedValue 的 getter）。在"默认 MainActor 隔离"下，它只能在主线程上同步调用。
  • 有些闭包会在后台运行。Task.detached、DispatchQueue.global().async 的闭包本来就在后台。RunLoop.main.perform、OperationQueue.main.addOperation 虽然实际在主线程执行，但它们的闭包签名只是 @Sendable，编译器并不知道会在主线程跑。
  • 所以在这些闭包里读 self.console，就是在非隔离的上下文里同步访问 MainActor 的属性。这属于跨隔离访问，编译器会报诊断。

C3为什么复制到局部常量就没问题了？

let console = console 这一行在函数体里执行，此时就在 MainActor 上，同步调用 getter 是合法的。之后闭包捕获的是这个局部常量，而不是 self。这个常量只是一个 Console 对象的引用，可以安全地交给后台闭包：

  • 它可以跨线程传递。Console 是 MainActor 隔离的类，这样的类自动就是 Sendable，所以能被捕获进 @Sendable 闭包。
  • 在后台也能直接调用。log 被标成了 nonisolated：它只是把消息追加进 Mutex 保护的 LogBuffer，再用 Task { @MainActor in … } 通知主线程刷新，所以任何线程都能直接调用，不需要 await（见 #00+ 深读）。

这一行把两件事分开了：在主线程上把值取出来；后台闭包只拿到一个可以跨线程传递的引用。

C4既然有些闭包直接写也不报错，为什么还要统一写？
  • 不用逐个判断。同一个函数里既有 MainActor 闭包，也有后台闭包，哪个会报诊断还取决于 API 有没有 @preconcurrency。函数开头统一复制一份，所有闭包就都安全了。
  • 以后切到 Swift 6 不用再改。现在 Swift 5 模式下只有 Task.detached 那一处报警告，但这是 Swift 6 下的错误，其他三处在 Swift 6 下也会报警告。
  • 可以直接当参数传。mainActorSyncFunction(console) 把同一个引用传给同步函数。
  • 只有用到后台闭包的函数才这样写。blockMainThread() 全程在主线程同步执行，没有逃逸到后台的闭包，就直接用 console。
为什么 @State 才会这样？如果 console 是 View 上普通的存储属性（let / var，类型 Sendable），SE-0434 允许在同一模块里从非隔离上下文同步读取它，实测上面 6 种闭包在两种模式下都不报诊断。问题出在 @State 把它变成了一个 MainActor 的计算属性。
C5局部的 console 和 self.console 是同一个东西，为什么一个要 await、一个不用？

因为 console.log(…) 这一行其实做了两件事，需要 MainActor 的只是其中一件：

Task.detached {
    let ref = self.console   // ① 读 View 的属性，拿到 Console 对象的引用
    ref.log("7 …")           // ② 对这个对象调用 log
}
步骤访问的是什么按谁的规则检查能否在后台做
① self.consoleView 的属性（@State 的 getter）View 的隔离：MainActor❌ 必须在主线程
② ref.log(…)Console 对象的方法Console 的规则：log 是 nonisolated✅ 任何线程

被 MainActor 保护的，是"View 身上的 console 属性"这条访问路径，不是 Console 对象本身。let console = console 把第 ① 步提前到函数体里，在主线程上做掉；闭包里只剩第 ② 步：

private func scheduleFromSyncContext() {   // 运行在主线程（MainActor）上
    let console = self.console              // ① 在主线程上读属性：合法
    Task.detached {
        console.log("7 …")                  // 只剩 ②：在后台也合法
    }
}

Swift 的隔离检查不是按"对象属于谁"判断的，而是按你通过什么途径访问判断的。拿到引用以后，对对象做什么，仍然按 Console 类自己的规则检查：log 是 nonisolated，哪里都能调用；它的 entries 是 MainActor 隔离的，在后台访问照样报错 main actor-isolated property 'entries' cannot be accessed from outside of the actor。局部常量没有绕过任何保护，只是把"读 View 属性"这一步放到了合法的地方。

打个比方：View 的 console 属性是主办公室里的一本通讯录，只能在主办公室翻；Console 对象是一栋房子，引用是它的地址；log 是门口的信箱，谁都能投信；entries 是屋里的东西，只有主线程这位管理员能动。不写 let，等于后台员工出发后再回头翻通讯录；写了 let，等于出发前在主办公室把地址抄在纸条上带走。到了地方，投信没问题，进屋动东西照样得找管理员。
C6新的 console 是副本还是引用？

是引用。Console 是 final class，类是引用类型，变量里存的是指向堆上对象的引用。let console = console 只复制了引用（引用计数 +1），堆上仍然只有一个 Console 对象：

  • 后台写的日志界面上看得到。console.clear()、console.log(…) 改的都是 View 显示的那个对象。
  • let 不代表对象不能改。它只表示这个局部常量不能再指向别的对象，对象内部的数据照样可以变。
  • 如果 Console 是 struct，这招就失效了。那样会真的复制一份，后台往副本里写日志，界面上什么都看不到。整个设计依赖它是类。
  • 生命周期会被延长。每个闭包都强引用这个对象，闭包运行完之前它不会被释放，即使用户已经离开页面。这里的闭包都很快执行完，没有问题；Console.log 内部刷新界面时用 [weak self]，是为了不让日志任务反过来延长 Console 的寿命。
C7为什么说 MainActor 隔离的类"自动是 Sendable"？

Sendable 防的是：同一个对象被多个线程同时访问。普通的类不安全：主线程和后台线程拿到同一个引用，可以同时改它的 var。

MainActor 隔离的类不一样：它的可变状态只能在主线程上访问，编译器在每个访问点都检查。在主线程上可以直接访问；在后台只能 await，先切到主线程再访问；不 await 直接访问就是编译错误。所以不管引用被复制给多少个线程，真正动手读写状态的永远只有主线程一个，而主线程是串行的。后台拿着引用，能直接做的只有使用 nonisolated 成员，而编译器保证这些成员本身是安全的。

引用传来传去不会带来风险，所以 Swift 规定（SE-0316）：标了全局 actor 的类型自动遵循 Sendable。本机实测（Swift 6 模式，默认 MainActor 隔离）：

final class Console {                    // 默认 MainActor 隔离
    var entries: [String] = []
    nonisolated func log(_ s: String) {}
}
nonisolated final class PlainBox { var entries: [String] = [] }

func requireSendable<T: Sendable>(_: T) {}

requireSendable(Console())               // ✅ 自动是 Sendable
requireSendable(PlainBox())              // ❌ type 'PlainBox' does not conform to the 'Sendable' protocol

let c = Console()
Task.detached { c.log("ok") }            // ✅ 引用带到后台，调用 nonisolated 方法
Task.detached { _ = c.entries }          // ❌ main actor-isolated property 'entries' cannot be accessed from outside of the actor

同理，actor 类型永远是 Sendable。让类成为 Sendable 的其他办法：所有存储属性都是 Sendable 的 let；像 LogBuffer 那样用 Mutex 保护可变状态；实在证明不了，才用 @unchecked Sendable 由自己担保。

C8另一种写法：捕获列表 [console]

捕获列表是闭包开头方括号里的一组名字。意思是：在创建闭包的那一刻就把这些值求出来，作为常量存进闭包，闭包运行时用存下来的值，而不是到时候再去外面读。

Task.detached { [console] in
    console.log("7 Task.detached")
}
DispatchQueue.global().async { [console] in
    console.log("8 global")
}

在方法里，闭包中写 console 实际是 self.console：

写法闭包里存了什么什么时候读 self.console
{ console.log("…") }self闭包运行时（可能在后台）
{ [console] in console.log("…") }Console 对象的引用创建闭包时（在主线程）

它和 let console = console 效果完全一样，只是作用于单个闭包。捕获列表在创建闭包的上下文里求值，在 MainActor 上创建闭包，就是在主线程上读属性，所以合法；之后闭包在哪运行都不影响这一步。

不写捕获列表和写了的区别，本机实测：

var n = 1
let a = { print(n) }          // 捕获变量 n 本身
let b = { [n] in print(n) }   // 创建时把 n 的值存进闭包
n = 2
a()   // 2：运行时去读变量
b()   // 1：用的是创建时的快照

final class Box { var v = 1 }
var box = Box()
let c = { [box] in print(box.v) }
box.v = 2      // 改的是同一个对象 → c() 打印 2（引用类型，快照的是引用）
box = Box()    // 变量改指向新对象 → c() 仍然打印 2（闭包还拿着旧对象）
写法含义
[console]捕获当前值，强引用
[weak self]弱引用，闭包里 self 是可选值，对象释放后为 nil，常用来避免循环引用
[unowned self]不增加引用计数也不可选，对象释放后访问会崩溃
[c = self.console]起个新名字，也可以是任意表达式，如 [count = items.count]
[console, weak self]多个用逗号分隔，可以混用

常见的 [weak self] 就是捕获列表的一种：同样在创建闭包时捕获 self，只是捕获成弱引用。

C9实际项目里一般用哪种？

三种写法本质相同：在主线程上把引用取出来，闭包或函数只带走引用。下面三种都在 Swift 6 模式、默认 MainActor 隔离下编译过，没有任何诊断。

场景推荐写法
只有一两个后台闭包捕获列表 { [console] in … }：最常见，意图一目了然
一个函数里有很多闭包都要用（如 OrderingDemo）函数开头 let console = console，最好加一句注释
真实业务代码别在 View 里开后台闭包：写成 @concurrent 函数，把需要的东西当参数传进去
@concurrent
static func work(_ console: Console) async {
    console.log("在后台做事")
}

func onTap() async {
    await Self.work(console)   // 参数在调用处求值：在主线程上读属性，再传过去
}

参数写法的好处：依赖写在函数签名上；可以 await 拿返回值，回到 MainActor 再更新状态；不需要 Task.detached，取消和优先级都能正常传递。

不推荐问题
await self.console / await MainActor.run { … }为了读一个引用多切换一次线程；GCD 这类同步闭包里写不了 await
nonisolated(unsafe)、@unchecked Sendable只是让编译器不再报错，问题还在

Support/Console.swift

13 个实验能成立，全靠日志说真话：记下的线程就是代码真实运行的线程，日志的顺序就是真实的执行顺序。做到这一点，需要两个类分工：

LogBuffer 的实现

nonisolated final class LogBuffer: Sendable {
    private struct State: Sendable {
        var entries: [LogEntry] = []
        var nextID = 0
        var start = ContinuousClock.now
    }

    private let state = Mutex(State())          // 所有可变状态都关在 Mutex 里

    func append(_ message: String) {
        let thread = ThreadInfo.current()      // ① 锁外：读当前线程（每个调用方自己的，不共享）
        state.withLock { state in              // ② 锁内：三件事作为一个整体完成
            state.entries.append(LogEntry(
                id: state.nextID,
                elapsed: state.start.duration(to: .now),
                message: message,
                isMainThread: thread.isMain,
                threadID: thread.id
            ))
            state.nextID += 1
        }
    }

    func snapshot() -> [LogEntry] { state.withLock { $0.entries } }   // 复制一份出去
    func reset() { state.withLock { $0.entries.removeAll(); $0.start = .now } }
}
Q1为什么要 Sendable？

Sendable 表示"这个值可以安全地在不同的并发域（线程 / actor / 任务）之间传递和共享"。LogBuffer 的整个工作就是被很多线程同时使用：

  • 它被跨隔离共享。同一个 buffer 对象由 MainActor 上的 Console 持有，又在 GCD 线程、协作线程池、actor 内部被调用 append。一个引用类型要在多个并发域之间共享，Swift 要求它是 Sendable，否则编译器无法保证没有数据竞争。
  • 它是 nonisolated let buffer 的前提。Console 是 MainActor 的类，想把它的某个存储属性标成 nonisolated（让非隔离代码直接读），编译器要求这个属性的类型是 Sendable。没有 Sendable，下面 Console 那一招就用不了。
  • 这里是编译器验证过的 Sendable，不是 @unchecked。一个 final class 要被自动认可为 Sendable，所有存储属性都得是不可变的 let，且类型本身 Sendable。LogBuffer 只有一个 let state: Mutex<State>，而 Mutex 本身是 Sendable 的，所以编译器能证明它安全。对比 #10 的 LockedBox：用 NSLock + var _value，编译器看不出锁和数据的关系，只能写 @unchecked Sendable 让人来担保。
  • LogEntry 和 State 也是 Sendable。条目在后台线程创建，最后通过 snapshot() 交给 MainActor，要跨越隔离边界，必须 Sendable。LogEntry 是只含值类型字段的 struct，天然满足。
Q2为什么 nonisolated？

工程开了"默认 MainActor 隔离"。不写 nonisolated，LogBuffer 就是 @MainActor 的，后台线程调用 append 时必须 await、先切到主线程。那样一来，后台的同步代码（GCD 闭包、concurrentPerform 的循环体）根本没法调用，就算能调用，也是先排队再记录，顺序和时间都不准了。nonisolated 让它变回一个"谁都能同步调用"的普通类，线程安全由 Mutex 负责，而不是由 actor 负责。

Q3state 为什么要包在 Mutex 里？

因为 append 会被多个线程同时调用。比如 #08 的 GCD 实验里，几个线程几乎同一时刻打日志。不加锁会出三类问题：

  • 数组本身被写坏。Array.append 不是线程安全的：两个线程同时 append，可能同时触发扩容、写同一个槽位，结果是丢日志、内存损坏甚至崩溃。
  • nextID 读改写丢失更新。nextID += 1 是"读、加一、写回"三步。两个线程同时读到 7，就会产生两条 id 都是 7 的日志。SwiftUI 的 List 用 id 区分行，id 重复时列表会显示错乱。这和 #10 "无保护"那一行是同一个 bug。
  • 顺序和时间对不上。elapsed 在锁内计算，所以"先拿到锁的先记时间、先拿 id、先进数组"，三者顺序一致。如果把计时放在锁外，可能出现 id 小的条目时间反而更晚。

反过来，ThreadInfo.current() 故意放在锁外：线程号是每个调用方自己的信息，不是共享状态，不需要保护；临界区越短，各线程等锁的时间越少。

Q4Mutex 是什么？

Mutex 是 Swift 6 标准库 Synchronization 模块里的互斥锁（SE-0433，iOS 18 / macOS 15 起可用）。它和传统锁最大的不同是：锁和它保护的数据绑在一起。

import Synchronization

let state = Mutex(State())                 // 数据被"装进"锁里
state.withLock { state in                  // 只能在加锁的闭包里拿到 inout 访问权
    state.nextID += 1
}                                          // 闭包返回 = 自动解锁，不会忘记 unlock
// state.nextID                            // ❌ 锁外根本访问不到数据

数据只能在锁内访问

传统写法 lock.lock(); value += 1; lock.unlock() 中，锁和数据只是"约定"上有关系，忘记加锁也能编译。Mutex 把值包在里面，withLock 是唯一入口，"忘了加锁"这种错误写不出来。

~Copyable：不能复制

Mutex 是不可复制类型。复制一把锁会得到两把各管各的锁，等于没锁，编译器直接禁止。也因此它通常作为 let 存在 class 里（LogBuffer 就是 class），由所有线程共享同一个实例。

本身是 Sendable

Mutex 无条件是 Sendable，这正是包含它的 final class 能被编译器自动认可为 Sendable 的原因，不需要 @unchecked。

同步、阻塞、不可重入

拿不到锁的线程会阻塞等待（Apple 平台底层是 os_unfair_lock）。闭包是同步的，不能在里面 await；同一线程在锁内再次 withLock 同一把锁会出错（死锁或崩溃）。所以临界区要短，只做几行内存操作。

"阻塞"在 Swift Concurrency 里不是不允许吗？#08 说过 async 代码里不能长时间阻塞，但持有时间以纳秒计的短锁是可以接受的：等待者很快就能拿到锁，不会拖垮协作线程池。append 的锁内只有一次数组追加和一次加法，符合这个条件。

Mutex 与主线程：四个追问

读到这里，自然会问：T2 等锁时为什么不用 await？主线程能不能用锁？有人持锁太久怎么办？调用方又怎么知道里面有锁？下面四个问题依次回答。

Q5T1、T2 同时 withLock，T2 要等，为什么不需要 await？

因为 T2 是阻塞在原地等，不是挂起，这正是 #02 讲的那组区别。await 是 Swift 用来标记"这里可能挂起、把线程让出去"的语法；withLock 是同步函数，从头到尾不让出线程，所以不需要、也不能写 await。

Mutex（withLock）actor（await）
等的方式阻塞：T2 的线程停在这一行，由系统挂起线程，T1 解锁后再唤醒它挂起：任务让出线程，线程去执行别的任务，轮到时再在某个线程上恢复
调用方写法普通同步调用，看起来只是"返回得慢了一点"必须写 await，只能在 async 上下文中调用
等待期间线程被占着，什么也不能做空出来做别的事
适合的等待时长极短（纳秒到微秒）任意长
state.withLock { … }   // T1 持锁时，T2 的线程停在这一行；T1 解锁后才进入闭包

为什么在这里阻塞可以接受？#08 说 async 代码里不能阻塞，指的是长时间阻塞：协作线程池的线程数约等于核心数，一个线程被长时间占住，其他任务就没有线程可用。LogBuffer 锁内只有一次追加和一次加一，持锁时间以纳秒计，T2 几乎立刻就能拿到锁。苹果平台上 Mutex 的底层是 os_unfair_lock，等锁的高优先级线程还会把优先级借给持锁线程，避免优先级反转。

同步阻塞也带来三条限制：

  • 锁里不能 await：闭包是同步的，写了编译不过。这是有意的设计：持锁时一旦能挂起，锁可能被占很久。
  • 锁里不做慢事：网络请求、文件 IO、Thread.sleep、等待其他线程的结果都不行。
  • 不可重入：同一线程在锁内再次 withLock 同一把锁，会死锁或崩溃。

也正因为只用 Mutex、不需要 await，Console.log 才能做成同步函数，GCD 闭包、concurrentPerform 循环体这类同步代码都能直接调用。换成 actor，这些地方就调用不了了。

Q6那主线程能用 Mutex 吗？会不会卡？

能用，这个工程的主线程就一直在用。会不会卡，看的是主线程等锁要等多久，跟锁本身无关：

  • 没有竞争（锁空闲，绝大多数情况）：一次原子操作，几十纳秒，不进内核，不会阻塞。
  • 有竞争（锁正被后台线程持有）：主线程要等对方解锁，等待时间约等于对方剩余的锁内工作时间。
对方锁内做了什么主线程等多久结果
数组追加、加一（LogBuffer）微秒级无感知
解码图片、写文件几到几十毫秒可能掉帧（60Hz 每帧约 16.7ms，120Hz 约 8.3ms）
网络请求、Thread.sleep几百毫秒以上明显卡顿

所以卡顿的根源是有人持锁太久，这个规则对所有线程都适用：后台线程的锁内工作也要短，因为主线程随时可能来等这把锁。

本工程的例子：Console.refresh() 和 clear() 都在主线程上调用 snapshot() 和 reset()，每打一条日志主线程就拿一次锁，App 并不卡。后台线程持锁只是一次 append；snapshot() 返回的 Array 是写时复制的，锁内只增加一次引用计数，不复制元素。有一个隐藏成本：snapshot 之后数组被两处共享，下一次 append 会在锁内触发一次完整复制（O(n)）。几百条日志可以忽略，几万条时就变成了"后台线程持锁太久"。

主线程用锁真正要防的是：

  • 锁里做慢事：不管哪个线程这样做，最终都可能让主线程等。
  • 死锁：后台线程持锁，再调用 DispatchQueue.main.sync，而主线程此刻正在等这把锁，两边互相等待，主线程永久卡死。规则是持锁期间不要同步等待任何其他线程。
  • 锁里调用外部代码：回调、delegate、发通知。你不知道它们会做什么，可能很慢，也可能回头再拿同一把锁。
Q7如果线程 T 持锁太久，主线程等着读数据，不就卡了吗？

会卡。主线程停在 withLock 那一行，T 持锁多久，它就停多久：界面不刷新，触摸没反应，TimelineView 停下（#02 的齿轮会停转）；卡到秒级，还可能在启动或切换前台时被看门狗杀掉（0x8badf00d）。优先级捐赠能让 T 跑得快一点，但 T 的工作量没变。

问题不在锁，而在主线程用阻塞的方式去等一个可能很久的东西。下面切换四种写法，看主线程的帧：

解法 1：缩短临界区（首选）。慢工作放到锁外，锁只保护最后那一下读写。只要所有线程都遵守"锁里只做内存操作"，主线程即使碰上竞争也只等几微秒。

// ❌ 锁里解码：持锁几十毫秒
state.withLock { $0.items = decode(data) }

// ✅ 锁外解码，锁里只赋值：持锁几十纳秒
let items = decode(data)
state.withLock { $0.items = items }

解法 2：主线程不硬等。Mutex 提供 withLockIfAvailable：拿不到锁就返回 nil，不阻塞。适合"晚一帧显示也无所谓"的 UI 刷新。要注意跳过的那次需要有人补上：Console 每条日志都会触发 refresh，中间跳过几次无妨；但如果最后一次被跳过，就再也没有触发了，需要自己安排重试。

func refresh() {
    if let snapshot = buffer.state.withLockIfAvailable({ $0.entries }) {
        entries = snapshot
    } else {
        // 锁正忙：这次先不刷新，稍后重试
    }
}

解法 3：把"等待"挪出主线程。让后台线程去等锁，主线程只 await，由阻塞变为挂起。代价是被阻塞的变成了协作线程池里的线程（#08），所以这只是转移问题，根本解法仍是解法 1。

@concurrent
static func readSnapshot(_ buffer: LogBuffer) async -> [LogEntry] {
    buffer.snapshot()                          // 在后台线程上等锁
}

entries = await Self.readSnapshot(buffer)      // MainActor 上：挂起，不阻塞

解法 4：本来就慢的工作，换 actor。如果受保护的逻辑本身包含耗时或异步操作，就不该用锁。用 actor，调用方 await，等待期间线程被让出，代价是 await 会传染到调用链，还有重入问题（#06）。

Q8可主线程根本不知道对象里面用了锁，怎么办？

这是关键所在：同步 API 不会告诉调用方它会不会阻塞。Swift 的类型系统里没有"可能阻塞"这个标记，await 只标记"可能挂起"。一个普通的同步属性或方法，内部可能在拿锁、调用 DispatchQueue.sync 或 semaphore.wait()、读文件（Data(contentsOf:)），或者同步调用某个跨进程的系统服务。从调用点看，它们和读一个普通变量写法完全一样。

// 调用点看起来一模一样，主线程无从分辨
let count = cache.count          // 也许只是读一个字段
let count = store.count          // 也许内部 withLock，而别的线程正在锁里写文件

那靠什么保证不卡？靠约定，责任在实现方。Swift 的设计思路是：同步 API 默认被认为很快，慢的东西要做成 async。

  • API 设计规范：属性访问应当很便宜；昂贵的操作做成方法；可能耗时很久的做成 async，让 await 在调用点把"这里可能要等"写出来。
  • 所以一个用 Mutex 实现的同步 API，对外承诺的是锁内只做短暂的内存操作。调用方最坏等多久取决于别人持锁多久，实现方保证这个时间极短，"同步调用不会卡"就仍然成立。
  • 实现方在锁里做 IO、解码、网络请求，又暴露成同步属性，就是实现方的 bug，和"getter 里偷偷发网络请求"是同一类问题，调用方无从防范。做不到短持锁，就应该改成 async API，或者内部改用 actor。
内部 Mutex · 同步 APIactor · async API
调用点能看出要等吗看不出能，必须写 await
等待时主线程阻塞挂起，照常响应 UI
谁保证不卡实现方，靠约定机制本身
代价无await 会传染到调用链；有重入问题

await 也不告诉你要等多久，但它保证等待期间主线程不会被占住。所以对"内部实现不透明、可能慢"的依赖，async API 更安全。

作为调用方，能做的：

  • 看 API 形态找线索：一个非 actor 的类型标了 Sendable，又提供同步读写方法，内部几乎一定有锁或原子操作。它保证线程安全，但不保证持锁时间。
  • 对可能很重的调用保持警惕：第三方 SDK 的同步 API、涉及磁盘或系统服务的 API，不要放进主线程的高频路径（滚动回调、每帧刷新）。拿不准时，包一层 @concurrent 函数在后台调用，主线程 await。
  • 用工具发现卡顿：Instruments 的 Hangs、Thread State Trace 能看到主线程卡在哪个锁或系统调用上；Xcode 的 Thread Performance Checker 在运行时提示优先级反转等风险；线上看 Xcode Organizer 的 Hangs 报告和 MetricKit 的 hang 诊断。
  • UI 侧的状态尽量不用锁：这正是默认 MainActor 隔离的好处。只在主线程读写的状态没有竞争，不需要锁，主线程也就不会去等别人的锁。本工程里 Console.entries 就是这样，只有跨线程的入口 LogBuffer 才用 Mutex。
回到这个工程：refresh() 在主线程调用 buffer.snapshot()，主线程确实"不知道"里面有锁。它能放心调用，是因为 LogBuffer 守住了约定：锁内只有一次追加、一次加一或一次引用计数增加。如果哪天有人在 append 的锁里加了写文件，日志一多，主线程就会卡在这里，而 refresh() 的调用点一个字都没变。

Console 的实现

@Observable
final class Console {                        // 默认隔离 → 整个类是 @MainActor
    private(set) var entries: [LogEntry] = [] // SwiftUI 读它：只在主线程改

    nonisolated let buffer = LogBuffer()      // ← 这一行的 nonisolated 是关键

    nonisolated func log(_ message: String) {
        buffer.append(message)                // 同步记录（在调用方线程）
        Task { @MainActor [weak self] in self?.refresh() }   // 异步刷新（在主线程）
    }

    func refresh() { entries = buffer.snapshot() }   // MainActor
    func clear()   { buffer.reset(); entries = [] }  // MainActor
}
Q9"Console 是 MainActor 隔离的类"，如何理解？

一句话：这个类的成员默认都归 MainActor 管，只有已经在 MainActor（主线程）上的代码才能直接使用它们。

1. 源码里没写 @MainActor，标注从哪来

工程开启了 Default Actor Isolation = MainActor，模块里所有没写隔离标注的类型，编译器都当作写了 @MainActor。所以源码里的 @Observable final class Console 实际等同于：

@MainActor @Observable
final class Console { … }

2. 每个成员归谁管

成员隔离能在哪直接用
private(set) var entriesMainActor只有主线程上的代码
func refresh()MainActor只有主线程上的代码

init()（隐式）MainActor只有主线程上的代码
nonisolated let buffer不属于任何 actor任何线程

所以"整个类是 MainActor 的"，更准确地说是：类上的标注给所有成员定了默认归属，单个成员可以用 nonisolated 退出。buffer 和 log 就是专门为后台线程开的两个口子。

3. 隔离带来的两条保证

  • 编译期：限制谁能直接访问。主线程上的代码（View 的 body、按钮回调、其他 MainActor 函数）可以直接读写 entries、调用 clear()；后台的 async 代码必须写 await console.clear()，先切到主线程再调用；后台的同步代码（GCD 闭包等）没法 await，所以不能调用，编译器报错（Swift 5 模式下有些地方只给警告）。
  • 运行期：通过正当途径调用时，代码一定在主线程上运行。await console.clear() 时，任务先被挪到 MainActor 的执行器上，而 MainActor 的执行器就是主线程。

两条合起来，entries 只会被主线程读写。主线程一次只做一件事，所以不需要加锁，也不会有数据竞争。这也是 SwiftUI 的要求：界面读的数据必须在主线程上修改。

4. 容易误解的地方

  • 它不是说"对象住在主线程上"。对象和别的对象一样在堆内存里，引用可以传给任何线程。隔离管的是"谁能访问它的哪些成员"，不管对象放在哪。这也是它能自动成为 Sendable 的原因（见 C7）：引用传到哪都没关系，受保护的成员只有主线程能碰。
  • 它不是一个运行时的锁。没有任何代码在每次访问时检查"现在是不是主线程"。保护主要靠编译器在调用处卡住；绕过编译器的路径（比如 Swift 5 模式下只给警告的 GCD 闭包），运行时照样会在后台执行。实测中，@MainActor 的同步函数被 GCD 闭包调用时，确实在后台线程上运行了。
  • nonisolated 成员不受这些保护。所以 log 不碰 entries：它只往 buffer 写，而 buffer 自己用 Mutex 保证线程安全。

5. 从 log 的实现看这个设计

nonisolated func log(_ message: String) {
    buffer.append(message)                              // 任何线程：写进 Mutex 保护的缓冲
    Task { @MainActor [weak self] in self?.refresh() }  // 交给主线程：读缓冲，更新 entries
}

log 可能在任何线程上被调用，所以它只做线程安全的事：写缓冲。真正修改 MainActor 状态 entries 的 refresh()，用 Task { @MainActor in … } 交回主线程去做。

一句话：MainActor 隔离的类，就是把这个类的状态和方法都划给主线程管。编译器保证别的线程只能"排队请主线程代办"，不能直接动手；只有标了 nonisolated 的成员，才对所有线程开放。
Q10buffer 为什么要 nonisolated？

Console 整个类是 MainActor 隔离的，它的存储属性默认也是 MainActor 隔离的，let 也不例外。而 log 是 nonisolated 函数，可能在任意线程上运行。在 log 里写 buffer.append(...) 就是"从非隔离上下文读取 MainActor 属性"，编译器会要求 await，同步调用就不成立了。

nonisolated let buffer 告诉编译器：这个属性不归 MainActor 管，任何线程都可以直接读。这件事之所以安全，是因为两个条件同时成立：

  • let：引用本身初始化后永不改变，多个线程同时读一个不变的引用，没有竞争。（nonisolated var 是不允许的，要写就只能用 nonisolated(unsafe) 自己担保。）
  • 类型是 Sendable：读到引用之后，调用它的方法也是安全的，因为 LogBuffer 内部用 Mutex 自己管好了并发。这就是 Q1 中"Sendable 是 nonisolated let 的前提"。

于是 Console 被切成两半：MainActor 的那一半（entries、refresh、clear）给 SwiftUI 用；非隔离的那一半（buffer、log）给全世界用。

Q11为什么用快照刷新，而不是每次 Task 里追加一条？

每次 log 都会启动一个 Task { @MainActor }，但非结构化 Task 的执行顺序没有保证（#01 演示过）。如果写成 Task { @MainActor in entries.append(entry) }，屏幕上的顺序就可能和真实顺序不同。

现在的 refresh() 不管自己是第几个被执行，都把 buffer 的完整快照复制过来。顺序由 buffer（也就是 Mutex）决定，与 Task 的执行顺序无关；多个 refresh 重复执行也没有副作用，最后一次总能显示全部日志。

  • [weak self]：页面关闭后，排队中的刷新不会让 Console 多活一段时间。
  • 捕获 self 本身没问题：Console 是 MainActor 隔离的类，自动是 Sendable。
  • 代价是每条日志都复制一次数组、启动一个 Task。演示里日志只有几十到几百条，可以接受；日志量很大时，可以加一个"已安排刷新"的标志来合并刷新。
Q12主线程被阻塞时，日志会不会乱？

不会，这正是"记录"和"显示"分开的好处。#02 里主线程被 Thread.sleep 卡住 2 秒，期间后台线程照样调用 log，条目、时间、线程号都同步写进了 buffer。主线程恢复后，排队的 refresh 才执行，一次性显示出来，时间戳仍然是事件发生时的真实时间。如果记录也要等主线程，这 2 秒内的日志时间就全是错的。

Q13ContinuousClock 是什么？

Swift 5.7（SE-0329）给标准库加了一套时间类型，代替过去 Date、DispatchTime、CFAbsoluteTime、mach_absolute_time 各管一摊的局面：

Clock · 时钟

一个协议：能告诉你"现在"（now），能睡到某个时刻（sleep(until:)）。标准库自带两个实现：ContinuousClock 和 SuspendingClock。

Instant · 时刻

某个时钟上的一个点，比如 ContinuousClock.now。可以比较大小、加减 Duration。它不是日历时间，没法转换成"几点几分"，只能和同一个时钟的另一个时刻比较。

Duration · 时长

两个时刻之差：start.duration(to: .now)。用 .seconds(2)、.milliseconds(100) 构造，精度到 attosecond（10⁻¹⁸ 秒），Task.sleep(for:) 接收的就是它。

ContinuousClock 是一个单调时钟：只会往前走，不受用户修改系统时间、网络校时、时区变化的影响，设备休眠期间也继续走。另一个 SuspendingClock 同样单调，区别只在于设备休眠时它暂停。

Q14为什么计时不用 Date？

Date 表示"日历上的某一时刻"，适合显示、存储、和服务器对时，但不适合测量时长：用户手动改时间、网络校时，都会让 Date() 突然跳动，两次 Date() 相减可能得到偏大甚至负的结果。日志的 elapsed 一旦为负，"谁先谁后"就无从谈起。单调时钟没有这个问题。

至于选 ContinuousClock 还是 SuspendingClock：演示里的实验都在几秒内跑完，期间设备不会休眠，两者测得的结果相同。ContinuousClock 是 Task.sleep(for:) 的默认时钟，用它和标准库保持一致。如果关心的是"进程真正运行了多久"（比如性能测量时希望排除休眠），就用 SuspendingClock。

        console.log("onTermination：\(reason)")
        ticker.cancel()          // 消费者不要了 → 停掉生产者
    }
    ticker.start()
}

细节：StreamTicker 的事件处理闭包用 [unowned self]，因为 DispatchSource 持有闭包，闭包再强引用 ticker 就成了环；ticker 的生命由 onTermination 闭包持有。produced 没加锁也安全，因为同一个 DispatchSource 的事件处理是串行执行的，代码注释里写了这一点，这也是这里用 @unchecked Sendable 的依据。

nonisolated struct RelativeTimeSchedule: TimelineSchedule {
    func entries(from startDate: Date, mode: TimelineScheduleMode) -> UnfoldFirstSequence<Date> {
        sequence(first: startDate) { date in
            let age  = date.timeIntervalSince(reference)
            let step = age < 60 && mode != .lowFrequency ? 1 : age < 3600 ? 60 : 3600
            return reference.addingTimeInterval((max(0, age) / step).rounded(.down) * step + step)
        }
    }
}
  • 自定义调度表标 nonisolated：不然在默认 MainActor 隔离下，这个值类型和它对 TimelineSchedule 的遵循都会被绑到主线程，而协议要求本身是非隔离的。
  • 时间点对齐到参考时间的整秒、整分，而不是"现在 + 60 秒"，于是"x 分钟前"恰好在跨过整分钟时更新。示例消息设成 55 秒前和 59 分 50 秒前，几秒内就能看到刷新频率切换。
  • ⑦ 在数组末尾多加一个时间点，这是实测出来的结论：iOS 26 上数组的最后一个时间点不会触发刷新。代码注释和卡片说明都写了这一点。

反复出现的写法

pattern → reason

13 个文件读下来，下面这几条写法反复出现。它们是这个工程的"实验方法"，换到自己的项目里写演示或排查问题时同样适用。

01一个页面只改一个变量

同一段工作（同样 2 秒的 spin、同样的 FakeAPI、同样的 hammer），只换执行方式。日志之间的差别就只来自这一个变量。

02把现象变成可以核对的数字或画面

停转的齿轮、峰值并发数、用过的线程数、⏱ 总耗时、已刷新次数、✅/❌。不需要读者盯着代码推理，看结果就能下结论。

03在事件发生的那一刻记录线程

Console.log 是 nonisolated 的同步函数，线程号在调用现场读取。日志一旦要先切回主线程才记录，测到的就永远是 main。

04显式写出隔离，不依赖默认值

默认 MainActor 让"不在主线程"成了需要显式声明的事。实验代码放进 nonisolated enum，要切到后台就写 @concurrent，代码的执行位置写在声明上。

05取消必须看得见

凡是可能被取消的地方都 catch 住 CancellationError 打一行日志，或者检查 isCancelled。看不到"被取消"的日志，就没法确认自动取消真的发生了。

06保管好句柄

@State consumer、onLeak 回调、CombineAsyncLab、cancellables：谁持有 Task 或 AnyCancellable，谁就负责它的生命周期。#11 和 #12 ⑤ 演示的就是不保管句柄的后果。

07危险写法单独标注

@unchecked Sendable、assumeIsolated、Work.block 在 async 中使用，每处都有注释说明为什么这样写、出错时会怎样；会死锁的 main.sync 只在说明文字里提到，没有做成按钮。

08实测结果写进代码注释

cadence 在 iOS 上总是 .minutes、.explicit 的最后一个时间点不触发刷新、perform(inModes:) 不会唤醒 RunLoop：这些都是实际跑出来的结果，记在代码旁边。
